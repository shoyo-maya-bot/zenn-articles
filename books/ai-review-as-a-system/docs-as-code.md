---
title: "設計書をGitHubで管理する：PRと自動チェックでレビューの土台を作る"
---

2章で、設計書をMarkdownにして、欠けていないかを確かめられるようになりました。次は、そのMarkdownをどこに置き、変更をどう確かめるかです。

この章では、設計書をコードと同じようにGitHubで管理する「Docs as Code」の始め方を、AIレビューにつなげる視点で整理します。書式チェックのスクリプトやワークフローの全文は、記事「[ドキュメントもGitHubで管理しよう](https://zenn.dev/shoyomayabot/articles/github-docs-pr-review-actions-lint)」に載せています。この章では、設計書に当てはめるときの考え方と、4章以降のAIレビューとのつなぎ方に絞って説明します。

## なぜAIレビューの前にGitHubなのか

AIレビューの仕組みを作るとき、GitHubで管理しておくと3つのことが手に入ります。

- **AIが読める場所にある。** リポジトリにMarkdownがあれば、エージェント型のAIがそのまま読めます。共有フォルダのWordを開いて貼り付ける手間がなくなります。
- **「何が変わったか」だけをレビューできる。** PRの差分があれば、AIにも人にも、変わった部分だけを見せられます。設計書全体を毎回読ませるより、速くて安くなります。
- **レビューの記録が残る。** どの指摘を受けて、どう直したかがPRに残ります。4章の「採択・不採択の記録」の土台になります。

## 全体の流れ

設計書の変更は、次の流れで扱います。

1. 作業用のブランチを作り、設計書を直す
2. PRを作る
3. GitHub Actionsが、書式と必須項目を自動でチェックする
4. AIがレビューし、人が採否を決める（4〜5章）
5. チェックとレビューが通ったら、mainにマージする

mainに入ったものだけが「正式な版」です。この「正式な版はどれか」がはっきりすることが、AIにとっても大事です。古い版を読んでレビューする事故を防げます。

## 手順1：フォルダ構成を決める

設計書なら、文書の種類ごとにフォルダを分けるのがおすすめです。

```text
design-docs/
  docs/
    api/            ← API定義書
    batch/          ← バッチ定義書
    screen/         ← 画面定義書
  originals/        ← 原本（Word・Excel）。.gitignore で除外するか、別の場所に置く
  config/
    checks.yaml     ← AIレビューの観点（4章）
  scripts/
    check-docs.mjs  ← 必須項目のチェック
  .github/
    workflows/
      check-docs.yml
    pull_request_template.md
  .markdownlint-cli2.jsonc
  README.md
```

種類ごとに分けておくと、4章で「API定義書にはこの観点、バッチ定義書にはこの観点」と、観点を切り替えやすくなります。

置き場所のルールは、必ずREADMEに書きます。人もAIも、READMEを見れば迷いません。

:::message alert
原本や変換結果に機密が含まれる場合、うっかりGitHubに上げないように注意してください。公開リポジトリには置かず、社内のリポジトリで管理しましょう。
:::

## 手順2：PRでレビューする流れにする

### PRテンプレートに「AIに見せる前の確認」を入れる

`.github/pull_request_template.md` を置くと、PRを作るたびにその内容が本文に入ります。設計書のPRなら、次のような項目がおすすめです。

```markdown
## 変更内容
<!-- 何を変えたかを1〜2行で -->

## 変更の理由
<!-- 仕様変更・不具合・指摘対応など。チケット番号があれば書く -->

## チェックリスト
- [ ] 原本を変えた場合、Markdownも再変換した（2章の変換レポートで loss.* が無い）
- [ ] 影響する他の設計書を確認した
- [ ] AIレビューの結果を確認し、採否を付けた
```

「変更の理由」は、AIにレビューさせるときにも役立ちます。理由が書いてあれば、AIは「この変更が理由に合っているか」という観点で見られます。

### mainを守る

PRとチェックを必須にするルールセットの設定は、記事のほうで手順を説明しています。設計書のリポジトリでも、同じ設定をそのまま使えます。

## 手順3：機械で分かることは機械でチェックする

GitHub Actionsでは、白黒はっきりするものだけをチェックします。設計書なら、次のようなものです。

| チェック | 例 |
| --- | --- |
| Markdownの書式 | 見出しの階層の飛び、表の列数の不一致 |
| 必須の項目 | 文書ID、版数、更新日 |
| 必須の見出し | API定義書なら「概要」「リクエスト」「レスポンス」「エラー」 |
| 命名のルール | ファイル名、文書IDの形式 |

Markdownの書式は markdownlint、必須の項目と見出しは小さなスクリプトで確かめます。スクリプトの書き方は、先ほどの記事にあるfront matterのチェックと同じ考え方です。「どの項目が必須か」を設計書の種類ごとに書き換えれば使えます。

エラーメッセージは日本語で、直し方が分かるように書くのがポイントです。

```text
docs/api/order-api.md: 必須の見出し「エラー」がありません
docs/api/order-api.md: 文書ID は API-000 の形式にしてください
```

人もAIも、このメッセージを見ればすぐに直せます。

## 役割分担：Actions・AI・人

ここまでで、機械のチェックが動くようになりました。4章からは、この上にAIのレビューを重ねます。その前に、誰が何を見るかを決めておきましょう。

| チェックする人 | 得意なこと | この本の章 |
| --- | --- | --- |
| GitHub Actions | 書式、必須項目、命名のルールなど、白黒はっきりするもの | この章 |
| AI | 記載の抜け、あいまいな表現、観点に照らした問題 | 4〜5章 |
| 人 | 事実が正しいか、業務として妥当か、最終判断 | 全章 |

大事なのは、**機械で分かることをAIに探させない**ことです。必須の見出しが無いことは、スクリプトなら一瞬で、しかも毎回同じ結果で分かります。AIに探させると、時間も費用もかかり、見落とすこともあります。

4章で紹介する仕組みでも、AIに見せる前に `harness precheck` で機械的な不足を潰しています。考え方はこの章と同じです。

## よくある失敗

**原本とMarkdownの両方を直す**
Wordも直し、Markdownも直していると、いつか食い違います。移行中は原本を正にして、Markdownは再変換で作る。移行が終わったらMarkdownを正にする。どちらが正かを、READMEに書いておきましょう。

**設計書の種類ごとに必須項目を分けない**
API定義書とバッチ定義書では、必要な見出しが違います。全部の種類に同じ必須項目を課すと、合わない文書でエラーが出続け、チェックが無視されるようになります。必須項目は、フォルダ（種類）ごとに決めましょう。

**チェックが0件でも緑になる**
対象のパスを間違えると、1件もチェックせずに成功します。「何件チェックしたか」を出力し、0件なら失敗にしておくと安心です。この考え方は、6章でもう一度出てきます。

**AIのレビュー結果をCIの合否にする**
AIの指摘は下書きです。PRにコメントするだけにして、合否は機械のチェックだけで決めます。採否は人が決めます。

## この章のまとめ

- 設計書をGitHubで管理すると、AIが読める場所にあり、差分だけをレビューでき、記録が残る
- PRテンプレートに「再変換したか」「変更の理由」を入れて、AIにも人にも分かりやすくする
- 書式や必須項目は、AIより先にGitHub Actionsでチェックする

これで、AIに渡す入力が整いました。次の章から、いよいよAIにレビューしてもらいます。
