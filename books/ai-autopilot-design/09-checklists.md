title: "9章 チェックリスト集とテンプレート"
---

この章は、ここまでの内容を「そのまま使える形」にまとめたものです。
新しい定期タスクを作るときや、既存のタスクを見直すときに使ってください。

## A. 新しい定期タスクを作る前のチェックリスト

### 任せ方

- [ ] 仕事を「戻せる」「戻せない」に分け、戻せない操作は人に残した
- [ ] 成果物を機械で確かめる手段がある
- [ ] 手順は手順書に固定し、AIには中身だけ作らせる
- [ ] 判断が必要なときの書き先（判断待ちの一覧）を決めた

### 守り

- [ ] 破られたら事故になるルールは、権限かフックで強制している
- [ ] 設定ファイルはAIが書き換えられない場所にある
- [ ] ダミーで本当に止まることを試した

### 判定と報告

- [ ] 終了コードと結果の中身の両方で成否を判定する
- [ ] 「未確認」を成功に数えない
- [ ] 何もなかった日も1行報告する
- [ ] 見張り役のタスクが、失敗・未実行・短すぎる成功を拾う

### 外部への書き込み

- [ ] 初期値はドライラン
- [ ] 送信の記録帳があり、「不明」があれば次を送らない
- [ ] 書き込む前にアカウントを照合する
- [ ] 件数・間隔・緊急停止をコードで強制する

### 再開とコスト

- [ ] 2回動いても壊れない（既存の確認、決まったブランチ名、同時実行の制限）
- [ ] 失敗を分類して、再試行してよいものだけ1回再試行する
- [ ] 1回分の消費を測ってから頻度を決めた
- [ ] 時間・回数・金額の上限がある

### プラットフォーム

- [ ] 外部への書き込みは1つずつ
- [ ] CIのポーリングは2分以上の間隔
- [ ] レート制限・停止の警告で即座に止まる
- [ ] 開始時刻を0分・30分からずらした

## B. 定期タスクの指示文テンプレート

定期タスクは毎回、何も知らない状態から始まります。
指示文だけで完結するように書きます。

```markdown
あなたは〇〇を担当します。毎週〇曜〇時に動きます。
ユーザーへの連絡は日本語で、スマホで読む想定で短く書きます。
ユーザーは「結果と、本当に判断が必要なことだけ見たい」と言っています。

## 【最優先】上限
- 外部への書き込み（push・PR・投稿）は1つずつ。1回の実行で最大〇件
- 結果待ちは2分以上の間隔で確かめる
- 403・429・レート制限・停止の警告が出たら、再試行せずに止めて報告する

## 最初にやること
- 必要な道具を読み込む
- 今日の分がすでにあるか確かめる。あれば何もせず終わる

## 毎回やること
1. 〇〇を確かめる
2. 〇〇を作る（手順は固定。迷ったら判断待ちに書いて止まる）
3. 機械で確かめる（テスト・lint・ファイルの存在）
4. 成果物を〇〇に置く

## 自分で決めてよいこと
- 〇〇、〇〇

## 判断待ちに回すこと（自分ではやらない）
- 費用が出るもの、削除、公開、外部への投稿、設定の変更

## 報告
- 最後に必ず報告する（何もなかった日も1行）
- 途中で止まったら、どの手順で何が起きたかをエラー文のまま伝える
```

## C. 外部に書き込むタスクに足す節

```markdown
## 投稿前の安全確認
- アカウントの確認：投稿を始める前に、管理画面のURLやアカウント名が
  〇〇（ID：〇〇）であることを確かめる。違う・確かめられないときは止めて報告する
- 二重投稿の防止：投稿の直前に記録帳へ「試行：〇〇」と書き、
  終わったら「成功（URL）」か「失敗（理由）」を書き足す。
  前の回の結果が書かれていない試行があれば、相手側の画面で
  その投稿がすでにあるか確かめてから進む
- 1回の実行の上限：最大〇件。再試行は1件につき1回まで
```

## D. AIへの作業依頼テンプレート

長い作業を頼むときは、完了条件を3つの部品で書きます。

```markdown
## やること
〇〇を実装する。

## 完了の定義
- 〇〇ができる状態になっている

## 確かめ方
- `npm test` と `npm run lint` が通る
- 〇〇の画面のスクリーンショットを添える

## 禁止事項
- 既存のテストを緩めない・消さない
- 依存パッケージを追加しない
- 変更してよいファイル：src/〇〇/ 以下だけ

## 報告に必ず入れること
- やったこと（証拠つき）
- できなかったこと（理由つき）
- 未確認のこと
```

「確かめ方」が書けないときは、その作業はまだAIに渡せる形になっていません。
もっと小さく分けるか、例を示すか、人がやるかを選びます。

## E. 受け入れの記録

AIの成果物を受け入れたときは、短くてよいので記録を残します。

```json
{
  "scope": "ログイン画面の入力チェック",
  "artifact": "commit abc123",
  "evidence": ["テスト12件通過のログ", "画面のスクリーンショット"],
  "unverified": ["Safari での表示"],
  "decision": "条件付きで受け入れ（Safari は次回確認）",
  "owner": "自分",
  "reason": "主要ブラウザで確認済み"
}
```

「条件付きで受け入れ」と「保留（証拠が足りない）」を分けて書くのがポイントです。
あとで見返したとき、どこまで確かめたかがすぐ分かります。

## F. 月に1回の見直し

- [ ] すべての定期タスクに、同じ上限のルールが入っているか
- [ ] 止めたタスクが有効なまま残っていないか
- [ ] 権限とフックが、今も意図どおり止まるか（ダミーで試験）
- [ ] 1回あたりの消費が増えていないか
- [ ] 判断待ちの一覧に、古いものが溜まっていないか
- [ ] 指示ファイルが長くなりすぎていないか（同じ指摘が2回出たら仕組みへ）
