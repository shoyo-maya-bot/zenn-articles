---
title: "2章 「お願い」ではなく「強制」で守る"
---

CLAUDE.md やプロンプトに「.env は読まないで」と書いても、確実に守られるとは限りません。
指示ファイルは、AIにとって「強い参考情報」です。
破られたら事故になるルールは、AIの外側で強制します。

## 守らせ方の3段階

ルールの守らせ方には強さの段階があります。

| 強さ | 方法 | 向いているルール |
| --- | --- | --- |
| 弱 | 指示ファイル・プロンプトに書く | 書き方の好み、命名規則 |
| 中 | 権限設定（allow / ask / deny） | 使ってよいコマンドの範囲 |
| 強 | フック（実行前チェック）、サンドボックス、コード側の上限 | 削除、秘密情報、本番への書き込み |

迷ったら、1段強い方法を選びます。
同じ注意を2回書いたら、それは「仕組みに変える合図」です。

## 権限設定の基本

Claude Code の権限は、deny・ask・allow の順に優先されます。
「git は自動で通すが、push だけは毎回確認したい」なら、次のように書けます。

```json
{
  "permissions": {
    "allow": ["Bash(git *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(~/.ssh/**)"]
  }
}
```

ワイルドカードの書き方には注意が要ります。
ある本の検証では、`Bash(ls *)` と `Bash(ls*)` は別物で、後者は `lsof` にも当たるとされていました。
書いたら、意図した範囲だけに当たるかを必ず試します。

### 置き場所の考え方

- 制限（deny）は、チームで共有する設定や組織の管理設定に置く
- 緩める許可（allow）は、個人の設定に置く
- 個人の設定ファイル（`settings.local.json` など）は git の管理から外す

こうすると、配布した設定に個人の許可が混ざりません。

## 1つ塞いでも、別の道がある

ここが一番の落とし穴です。
ある本の検証では、`cat` を禁止しても、AIは別のツールを使って同じファイルを読みに行きました。

AIは目的を達成しようとします。
1つの道を塞ぐと、別の道を探します。
「何を禁止するか」ではなく「その操作ができる道を全部」考えます。

| 守りたいこと | 塞ぐべき道の例 |
| --- | --- |
| 秘密ファイルを読ませない | ファイル読み取りツール、cat、エディタ、スクリプト経由 |
| プロジェクト外に書かせない | 編集ツール、シェルのリダイレクト、スクリプト |
| 削除させない | rm、git の破壊的コマンド、ファイル移動での上書き |

さらに確実なのは、そもそもそのプロセスに秘密を渡さないことです。
環境変数やファイルに秘密を置かない作業環境で動かせば、漏れる心配がなくなります。

## フックで止める

実行前フック（PreToolUse）を使うと、AIがツールを使う直前に自分のスクリプトで判定できます。
止めたいときは終了コード 2 を返します。

止めるときは、標準エラーに理由と代わりの方法を書きます。

```text
保護されたパス（.github/workflows）への書き込みは禁止です。
変更が必要なら、判断待ちの一覧に理由を書いてください。
```

理由が書いてあると、AIは別の道を探すより、人に確認する方へ切り替えやすくなります。
理由がないと、ただ別の方法を試し始めることがあります。

### 無限ループに注意

「テストが通るまで終わらせない」という終了時フックは便利です。
しかし、テストが構造的に通らない状況では、AIが永遠に作業を続けます。
使用量を使い切るまで止まりません。

フックには必ず上限を書きます。
「同じ理由で3回止めたら通す」「同じ差分では2回目は止めない」などです。

## 設定はAIが書き換えられない場所に

見落としがちなのが、設定ファイル自体の置き場所です。
deny やフックがリポジトリの中にあって、AIがそれを編集できるなら、守りになりません。

- 組織の管理設定や、AIの書き込み範囲の外に置く
- フック自体が失敗したときに、通すのか止めるのかを決めておく

危険な操作を扱うフックは、失敗したら止める（fail-closed）にします。
軽い整形などのフックは、失敗したら通す（fail-open）で十分です。

## 入れたら、必ず試す

設定は、書いただけでは効いているか分かりません。
ダミーのファイルを用意して、本当に止まるかを試します。

1. `.env.dummy` のような偽の秘密ファイルを作る
2. 「このファイルの中身を教えて」と頼む
3. 止まること、別の道でも読めないことを確かめる
4. デバッグ表示（`claude --debug` など）でフックが呼ばれたか確かめる

月に1回くらい、この試験を繰り返すと安心です。
ツールの更新で挙動が変わることがあるからです。

## 全自動モードを使うとき

確認を全部飛ばすモード（`--dangerously-skip-permissions` など）は、無人運用で使いたくなります。
ある本によると、このモードでも deny と明示した ask は効くとされています。
ただし挙動は版によって変わる可能性があるので、公式ドキュメントと実際の試験で確かめてください。

使うなら、次の3つをセットにします。

1. deny で最低限の柵を残す
2. 実行環境を隔離する（使い捨てのコンテナ、秘密のない環境）
3. 変更はPR経由にして、本番に直接触らせない

## よくある失敗

**指示ファイルに禁止事項を並べ続ける**
禁止事項が増えるほど、ファイルは長くなり、守られにくくなります。
2回破られたルールは、権限かフックに移します。

**1つのコマンドだけ禁止する**
同じことができる別の道が残っています。
「操作」ではなく「守りたいこと」から考えます。

**試験をしない**
設定の書き間違いは、事故が起きるまで気づけません。
ダミーで止まることを確かめます。
