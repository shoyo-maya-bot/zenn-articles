---
title: "3章 「できました」を信じない成功判定"
---

無人運用で一番怖いのは、失敗ではありません。
失敗しているのに「成功」に見えることです。
この章では、成功を機械で判定する方法を扱います。

## 「成功」が嘘になる3つのパターン

### パターン1：エラーなのに終了コードが0

ある本の検証では、認証が切れた状態でも、AIのCLIが「成功」の形をした結果を返し、終了コード0で終わることがあったと報告されています。
終了コードだけを見ていると、何もしていないのに成功扱いになります。

対策は、終了コードと結果の中身の両方を見ることです。

```bash
claude -p "..." --output-format json > result.json
# 終了コードに加えて、結果のエラー印も確かめる
jq -e '.type == "result" and .is_error == false' result.json
```

JSONが読めないときも、失敗として扱います。
「読めなかったから分からない」を成功にしないことが大切です。

### パターン2：AIが「直しました」と言っている

AIの報告は、証拠ではありません。
報告には、次のどれかを必ず付けさせます。

- 修正前に失敗し、修正後に成功したテストの出力
- 画面のスクリーンショット
- 実際のファイルの差分

依頼文に「主張ごとに証拠を添えること。証拠がない主張は『未確認』と書くこと」と入れておきます。

### パターン3：処理は動いたが、中身がない

定期タスクが「成功」で終わっていても、作業時間が極端に短いことがあります。
動画を作るタスクが1分で終わっていたら、何かがおかしいはずです。

見張り役のタスクを別に用意して、次を確かめさせると効果的です。

| 確かめること | 判断 |
| --- | --- |
| 予定時刻に動いたか | 動いていなければ報告 |
| 失敗していないか | 一時的な失敗なら1回だけ再実行 |
| 作業量に見合う時間がかかったか | 極端に短ければ「確認を」と報告 |
| 成果物が実際にできているか | ファイルの存在・件数を確かめる |

## 判定は「合格・不合格・未確認」の3つ

成功か失敗かの2つで考えると、判断できないものが無理やりどちらかに入ります。
3つ目の箱「未確認」を用意します。

| 判定 | 意味 | 例 |
| --- | --- | --- |
| 合格 | 証拠があり、条件を満たした | テストが通った出力がある |
| 不合格 | 証拠があり、条件を満たさなかった | テストが落ちた |
| 未確認 | 判断する材料がない | タイムアウト、ファイルが読めない、基盤の停止 |

欠けている値を「成功」で埋める仕組みは危険です。
壊れたときほど合格してしまうからです。

## 試行回数のワナ

「3回試して3回成功したから大丈夫」は、信頼性が高い証拠になりません。
ある本の試算では、成功率80%のエージェントでも、3回連続で成功する確率は約51%あります。

計算すると、次のとおりです。

```text
0.8 × 0.8 × 0.8 = 0.512
```

つまり、5回に1回失敗するエージェントでも、半分くらいの確率で「3回とも成功」に見えます。
試行回数は先に決め、結果を見て足さないようにします。
失敗した試行も記録から消しません。

## 作る人と確かめる人を分ける

同じ会話の中でAIに自分の成果物をレビューさせると、自分の前提の範囲しか見ません。
確かめる役は、別の文脈（別のサブエージェント、別のセッション）にします。

ある本の記録では、実装と別の文脈でレビューさせたところ、重大な指摘が多数見つかり、作者が先に気づいていたものはほとんどなかったと報告されています。
モデルを変えることより、文脈を分けることが効くという結論でした。

レビューの仕組み全体は大きなテーマなので、この本では深入りしません。
ここでは「作った文脈で合格を出させない」という1点だけ押さえてください。

## AIが書いたテストも疑う

AIにテストを書かせると、テストの数は増えます。
しかし、そのテストが本当に守りたいものを見張っているとは限りません。

確かめ方は簡単です。

1. 守りたい安全装置を一覧にする（上限、間隔、入力チェックなど）
2. 1つずつ、その装置を無効にする小さな変更を入れる（`if False:` にするなど）
3. テストが落ちるかを見る

落ちなければ、そのテストは装置を見張っていません。

**最重要の注意**：この試験の前に、外部やデータベースへの接続を遮断してください。
安全装置を外した状態のコードが、本番に接続しに行く危険があります。

## 報告は毎回、必ず送る

無人タスクは、何もなかった日も1行報告させます。

```text
CI 全緑、進める項目なし
```

黙って終わると、「何もなかった」のか「止まっていた」のか区別できません。
報告がない日は異常、と決めておけば、見張りが楽になります。

## よくある失敗

**終了コードだけで判定する**
結果の中身にエラー印があっても見逃します。
中身も必ず確かめます。

**「未確認」を成功に数える**
タイムアウトや読み取り失敗を成功扱いにすると、壊れた日ほど成功が増えます。

**AIのテストの数で安心する**
数は品質を表しません。
装置を外して落ちるかを確かめます。
