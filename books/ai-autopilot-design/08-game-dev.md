---
title: "8章 ゲーム制作にAIを使うときの型"
---

ゲーム制作は、AIに任せやすい部分と、任せにくい部分がはっきり分かれます。
コードは書けても、「気持ちいいか」はAIには判断しにくいからです。
この章では、Unity を例に、AIと作るときの型を紹介します。

## 構造を先に作らせる

AIは、最初に作った構造を増やしていく傾向があります。
最初の一歩で、機能まで作らせないことが大切です。

1. 最初のステップでは、空の起点（ゲームを起動するクラス）とフォルダ構成だけ作らせる
2. 機能は1ステップに1つずつ
3. 毎回「コンパイル → テスト全件 → プレイして目で確認」で締める

### 規約をコンパイルで強制する

Unity なら、Assembly Definition（asmdef）でコードを層に分けられます。

| 層 | 中身 | 参照してよいもの |
| --- | --- | --- |
| Logic | ルール・計算（MonoBehaviour を使わない） | なし |
| Presenter | ロジックと見た目の仲介 | Logic |
| View | 画面・UI・アニメーション | Presenter |
| Tests | テスト | Logic |

Logic から View を参照できないので、AIが規約を破るとコンパイルエラーで止まります。
2章の「お願いではなく強制」を、ゲームのコードでも使う形です。

### 書かせない書き方を決める

指示ファイルに「やってはいけないこと」を短く書いておきます。

```text
- async void は使わない（例外が拾えず、止められない）。非同期は UniTask と CancellationToken で
- 調整したい値（速度、時間、点数）はコードに直接書かず、設定アセットに出す
- 乱数と時刻はインターフェースで外から渡す（テストで固定できるように）
- 状態遷移は「状態が次の状態を返す」形にする
```

最後の状態遷移の型は、次のような形です。

```csharp
public interface IState { IState Run(); }

// 本体はこれだけ
_current = _current.Run();
```

遷移が二重に起きることが構造上なくなり、AIに書かせても形がぶれにくくなります。

## 初回は「粗い版」と明言する

最初の依頼では、完成品ではなく「レビューできる粗い版」を頼みます。
そして、次を書かせます。

- どこが仮の実装か
- 既知の不足
- テストが足りない場所

完成を装わせないことが大切です。
見て不満が多ければ、継ぎ足して直すより、早めに捨てて作り直すほうが速いことがよくあります。
追加の依頼を何回まで重ねるか、先に決めておきます。

## 演出は数値で頼む

「気持ちよくして」「いい感じに」と頼むと、出来がぶれます。
数値で頼みます。

| 項目 | 目安 |
| --- | --- |
| 入力から最初の反応まで | 100ミリ秒以内 |
| 画面の揺れ | 0.1〜0.3秒で、なめらかに弱まる |
| ヒットストップ | 3〜12フレーム（約0.05〜0.2秒） |
| UIを順番に出すときの段数 | 多くて3段まで |
| 効果音のピッチの揺らぎ | 毎回少しだけランダムに変える |

これらは Game Feel を扱った本や、アニメーションライブラリの本で紹介されている目安を、筆者がまとめたものです。
作品に合わせて調整してください。

### 光・音・揺れは同じフレームで

ヒットの手応えは、複数の感覚が同時に来ることで生まれます。
音が少し遅れるだけで、バラバラに感じます。
効果音は、演出と同じ処理の中から鳴らします。

### 演出は1つずつ外して確かめる

演出は、それぞれ独立してオン・オフできる部品にします。

- 入力の応答
- 見た目（光、パーティクル）
- 音
- カメラ（揺れ）
- 時間（ヒットストップ、スロー）

1つずつ外してプレイし、どれが効いているかを確かめます。
部品になっていれば、AIに「揺れだけ弱めて」と頼みやすくもなります。

### 演出は中断できる前提で

演出のスキップは、あとから必ず求められます。
最初から、まとめて止められる作りにします。
アニメーションはまとめて管理し、オブジェクトが消えるときに止めます。

## 事故を防ぐ小さな決まり

**.meta ファイルを git で管理する**
`.gitignore` の書き方によっては、Unity の `.meta` ファイルが管理から外れます。
すると、PCを変えたときにスクリプトの参照が全部切れることがあります。
`.gitignore` に次の1行を足して確かめます。

```text
!/[Aa]ssets/**/*.meta
```

**スケールは初日に決める**
3Dは1単位を1メートル、2Dは1単位を1ピクセルなど、最初に決めます。
あとから変えると、素材を作り直すことになります。

**デバッグ用の近道を用意する**
無敵、全部解放、スクリーンショットのキーを1か所にまとめます。
難易度の調整が速くなり、AIに確認させるときにも使えます。

**Blender から書き出す前に変形を確定する**
Blender で作ったものは、書き出す前に変形（位置・回転・拡大）を確定します。
やらないと、ゲームエンジン側で向きや大きさが狂います。

## 最初の1ステージを製品品質で

販売を考えているなら、最初の1ステージだけを、見た目もシステムも完成に近い状態で作ります。
これを「バーティカルスライス」と呼びます。

これで手に入るもの：

- 目指す品質の基準
- 残りのステージを作る見積もり
- ストアページや紹介動画の素材

見落としやすい作業も、早めに洗い出せます。
最適化、読み込み時間、解像度の対応、体験版の準備などです。

## よくある失敗

**最初から機能を全部頼む**
構造が固まる前に機能が増え、あとから直せなくなります。

**演出を言葉だけで頼む**
数値で頼み、1つずつ外して確かめます。

**AIの「動きました」で次へ進む**
プレイして目で確かめるまでが1ステップです。
