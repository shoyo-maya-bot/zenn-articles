---
title: "5章 止まっても再開できる作り"
---

無人タスクは、必ずどこかで止まります。
ネットワーク、使用量の上限、PCのスリープ、サービスの障害。
止まらない仕組みを目指すより、止まっても再開できる仕組みを作るほうが現実的です。

## 何度実行しても同じ結果になるように

同じタスクが2回動いても、結果が壊れないようにします。
これを「冪等（べきとう）」と呼びます。

GitHub を使う作業なら、次の4つが基本です。

| やり方 | 効果 |
| --- | --- |
| 成果物はPR経由で出す | main を直接壊さない |
| 着手前に、既存の成果物を確かめる | 同じものを2回作らない |
| ブランチ名を日付で決める（`nightly/fix-20261023`） | 2回目の実行が同じブランチを見つけられる |
| 同時実行を1本に制限する（GitHub Actions の `concurrency`） | 並走による衝突を防ぐ |

「今日の分はもうあるか」を最初に確かめる。
これだけで、再実行がずっと安全になります。

## 長い作業は区切って、状態をファイルに残す

1回で終わらない長い作業は、短い区間に分けます。
そして、どこまで進んだかをファイルに残します。

```json
{
  "cursor": "task-3",
  "checkpoints": ["a1b2c3d", "e4f5g6h"],
  "budget": { "usd_cap": 5, "used": 1.2 },
  "last_progress_at": "2026-10-23T08:00:00+09:00",
  "status": "running"
}
```

区間ごとに、検証が通ったコミットを記録します。
途中で止まったら、最後の検証済みのコミットから再開します。

終わったときの状態も、あらかじめ決めておきます。

| 状態 | 意味 |
| --- | --- |
| done | 完了 |
| awaiting_acceptance | 人の受け入れ待ち |
| blocked | 判断が必要で止まった |
| over_budget | 予算を使い切った |
| stalled | 進まなくなった |

### 「進んだ」の定義を厳しくする

エラーメッセージが変わっただけでは、進んだとは言えません。
進捗とみなすのは、次のどちらかのときだけにします。

- 同じ検証範囲で、失敗の数が減った
- 検証が通ったチェックポイントが増えた

この定義がないと、AIは同じ場所をぐるぐる回り続けることがあります。

## 再試行は「分類してから1回」

失敗したら全部再試行、は危険です。
失敗を分類してから決めます。

| 失敗の種類 | 対応 |
| --- | --- |
| 一時的（ネットワーク、タイムアウト） | 間隔をあけて1回だけ再試行 |
| 認証切れ | 再試行しない。人に知らせる |
| 使用量・課金の上限 | 再試行しない。回復後に動かす |
| レート制限・アカウントの警告 | 即座に止める（6章） |
| ロジックの誤り | 再試行しても直らない。判断待ちに回す |

外側で3回再試行すると、予算も最大4回分使います。
再試行の回数は、全体で決めておきます。

## 修正ループの上限

「直す → 確かめる → まだダメなら直す」のループにも上限を付けます。
ある本の例では、初回の実装と、最大2回の修正までとしていました。

上限に達したら、次のようにします。

1. 自分のコミットを取り消す（main を壊したままにしない）
2. 試したことと、失敗した理由を記録する
3. 判断待ちの一覧に、選択肢とおすすめを書く

人は判断待ちの一覧を見て、選ぶだけで済みます。

## 使用量の上限に当たった日は、粘らない

使用量の上限に当たったら、その日は直そうとせず翌日に回します。
上限の中で粘ると、ほかのタスクの分まで使ってしまい、失敗が連鎖します。

上限が回復したかどうかは、見張り役のタスクが判断できます。
見張り役が動いているなら、上限は回復しているとみなせます。
その時点で、上限で止まったタスクを優先順に動かし直します。

## 中断するときは「頭の中身」を残す

人が作業を中断するとき、頭の中にある「次にやること」は消えてしまいます。
AIも同じです。
セッションをまたぐ前に、引き継ぎメモを書かせます。

```text
## 引き継ぎ
- やったこと：ログイン画面の入力チェックを追加（テスト通過、コミット abc123）
- 次にやること：パスワード再設定画面
- 分かったこと：日付ライブラリは v3 で書き方が変わっている
- 未確認：Safari での表示
```

再開するときは、メモを鵜呑みにせず、実際の状態を確かめ直します。
メモに「テスト通過」とあっても、もう一度テストを回します。

## よくある失敗

**毎回新しいブランチ名で作る**
再実行のたびにPRが増えます。
日付などで決まった名前にします。

**全部の失敗を同じように再試行する**
認証切れやレート制限で再試行すると、状況が悪化します。

**進捗の定義がない**
AIが同じところを回り続け、予算だけが減ります。
