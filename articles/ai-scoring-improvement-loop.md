AIにコードを直させると、「改善しました」と報告してくれます。でも、本当に良くなったのかは、報告だけでは分かりません。

この記事では、**AIに採点させて、その点数を上げていく改善ループ**を紹介します。個人で公開しているリポジトリ15個に対して、採点と修正を5周まわしました。平均点は73点から、およそ85点まで上がりました。

一番のポイントは、**採点する役と直す役を分けること**です。

## なぜ役を分けるのか

同じAIに「採点して、直して、また採点して」と頼むと、点数は簡単に上がります。ただしそれは、品質が上がったからとは限りません。

- 自分が直したところを、甘く見てしまう
- 「直した」という記録（変更履歴など）を見て、直ったと思い込む
- 採点の基準を、知らないうちに自分に合わせて緩める

人のチームでも、自分のコードを自分でレビューすると見落としが増えます。AIも同じです。

そこで、採点は毎回**別のAI（サブエージェント）**に、まっさらな状態でやらせます。

## 採点役の設定

### 立場を決める

採点役には、次の立場を与えます。

```markdown
あなたは、このリポジトリを初めて見る、厳しめのシニアエンジニアです。

- これまでの採点結果や、修正の経緯は知りません
- CHANGELOGやREADMEの「改善しました」という記述は信用せず、コードとテストで確かめます
- ファイルの変更やpushは一切しません（読むだけ）
```

「初めて見る」と「変更履歴を信用しない」が大事です。前の周の結果を知っていると、「前より良くなった」という見方に引っ張られます。

### 点数の目安を決める

100点満点といっても、何点なら良いのかが決まっていないと、点数がぶれます。そこで目安を書いておきます。

| 点数 | 目安 |
| --- | --- |
| 70点台 | よくできた個人のOSS |
| 85点以上 | 社内にそのまま展開できる品質 |

目安があると、採点役が変わっても、点数の意味がそろいます。

### 採点の項目と配点

| 項目 | 配点 |
| --- | --- |
| 正しさ・堅牢性 | 25 |
| テスト・CI | 20 |
| セキュリティ | 15 |
| 設計・保守性 | 15 |
| ドキュメント・使いやすさ | 15 |
| AIからの使いやすさ・運用のしやすさ | 10 |

最後の項目は、AIエージェントから使われることを前提にしたツールだからです。出力の形や終了コードがそろっているか、などを見ます。

### 減点には根拠を付けさせる

採点で一番大事なルールです。

```markdown
- 減点するときは、必ず「ファイル名:行番号」の根拠を付ける
- 根拠を確かめられないものは「推測」と明記する
```

根拠がないと、「なんとなく保守性が低い」のような、直しようのない指摘が増えます。行番号まであれば、直す役はそこを見ればいいだけです。

### 出力の形を決める

各リポジトリについて、次の形で返させます。

- 合計点
- 6項目それぞれの点数
- 減点の理由3〜5個（根拠付き）
- 次に直すべきこと上位3つ

「上位3つ」に絞るのがコツです。指摘が多すぎると、直す役が手を広げすぎて、どれも中途半端になります。

## 改善ループの流れ

1. **採点する。** 採点役を、リポジトリごとに新しく立ち上げる
2. **直す。** 直す役が、「直すべきこと上位3つ」を中心に修正する
3. **テストとCIを通す。** 通らない修正は採用しない
4. **もう一度採点する。** 新しい採点役で、まっさらな状態から採点する
5. **点数と指摘を記録する。** 周ごとの変化を表にする

## 結果

| 周 | 平均点 | 85点以上のリポジトリ |
| --- | --- | --- |
| 1周目 | 73点（60〜79点） | 0個 |
| 2周目 | 約76点 | — |
| 3周目 | 約84点 | 6個 |
| 5周目 | 約85点 | 7〜8個 |

3周目までは大きく伸び、そこから先は伸びが小さくなりました。簡単に直せるところが先に片づき、残るのは設計に関わる重い課題だからです。

### 点数のぶれは±3点ほど

採点役は毎回新しく立ち上げるので、同じリポジトリでも点数が少しぶれます。今回は±3点ほどでした。

なので、1〜2点の上下で一喜一憂しないことが大事です。周をまたいだ傾向と、指摘の中身を見ます。

## 採点で多かった指摘

15個のリポジトリで、くり返し出た指摘がありました。

**間違った結果を、黙って返す**
入力が不正なのに、「0件、成功」として終わってしまう。エラーで止まるより、気づきにくくて危険です。

**Windowsで試していない**
CIがLinuxだけで、Windowsでの動作を確かめていない。利用者にWindowsが多いなら、CIにも入れるべきです。

**Pythonの依存パッケージのバージョンを固定していない**
いつかパッケージが更新されたときに、急に動かなくなる可能性があります。

どれも、作った本人は気づきにくいところです。初めて見る立場の採点役だからこそ、見つけられた指摘だと思います。

## 点数をごまかす修正に気をつける

点数を目標にすると、点数を上げるためだけの修正が紛れ込むことがあります。

実際に、`test_score3.py` という名前のテストが、採点役から「採点を意識したテストに見える」と指摘されたことがありました。中身が採点対策でなくても、そう見える名前は良くありません。

直す役への指示には、次のことを入れておきます。

- テストやチェックを緩めて点数を上げない
- 採点の項目名をそのままファイル名や関数名にしない
- 点数ではなく、指摘された問題そのものを直す

## 書き込みの量に上限を付ける

15個のリポジトリを何周も直すと、GitHubへの書き込みがとても多くなります。この作業の途中で、1日に約50本のプルリクエストを作ったところ、GitHubのアカウントが凍結されました（詳しくは[別の記事](https://zenn.dev/shoyomayabot/articles/github-account-suspended-ai-agent)に書いています）。

その後は、書き込みに上限を付けています。

| 項目 | 上限 |
| --- | --- |
| 同時に書き込む作業 | 2つまで |
| プルリクエスト | 1日10本まで |
| push | 1日30回まで |
| 403・429・セカンダリレート制限のエラー | 出たらすぐ止める |

AIは疲れないので、放っておくと人ではありえない量の書き込みをします。量の上限は、最初から決めておきましょう。

## よくある失敗

**同じAIに採点と修正をさせる**
点数は上がっても、品質が上がったとは限りません。採点役は毎回新しく立ち上げましょう。

**点数の目安を決めない**
採点役によって、70点の意味がばらばらになります。「何点ならどの程度か」を書いておきましょう。

**根拠のない減点を許す**
直しようのない指摘が増えます。「ファイル名:行番号」を必須にしましょう。

**1〜2点の変化で判断する**
採点にはぶれがあります。傾向と指摘の中身で判断しましょう。

**書き込みの量を気にしない**
短時間に大量のプルリクエストやpushをすると、サービス側から制限されることがあります。

## まとめ

AIに品質を上げさせるときは、「直した」という報告ではなく、別の目で測った点数で確かめます。

- 採点役と直す役を分ける。採点役は毎回まっさらにする
- 点数の目安と配点を決め、減点には根拠を付けさせる
- 点数のぶれを前提に、傾向で判断する
- 点数をごまかす修正と、書き込みの量に気をつける

これは、人のチームでの「レビューは書いた本人以外がやる」と同じ考え方です。AIを増やせるからこそ、役割を分けて、互いに確かめ合う形が作りやすくなります。
