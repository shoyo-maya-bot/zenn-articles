設計書のレビューをAIに頼むと、指摘がたくさん返ってきます。ところが、その中には的外れなものも混ざります。毎回「これは違う」と人が弾くだけでは、AIは次も同じ指摘をしてきます。

この記事では、AIレビューの結果に人が採択・不採択を付けて記録し、その記録からチェックリストそのものを改善していく仕組みを紹介します。実物は [office-review](https://github.com/shoyo-maya-bot/office-review) リポジトリで公開しています。観点やサンプルは、特定の企業・案件のものではなく、一般的な内容で作り直したものです。

## なぜ「育てる」必要があるのか

AIのレビューがうまくいかない理由は、大きく2つあります。

- **観点があいまい。** 「分かりやすく書かれているか」のような観点だと、AIは何でも指摘できてしまいます。
- **当てはめてはいけない場面を知らない。** 一般論としては正しい指摘でも、その文書では関係ないことがあります。

どちらも、最初から完璧なチェックリストを作るのは難しい問題です。そこで、実際のレビュー結果から少しずつ直していく、という考え方をとります。

## 全体の流れ

| 手順 | やること | コマンド / 操作 |
| --- | --- | --- |
| 1 準備 | Officeの原本をMarkdownにして置く | `harness convert 設計書.xlsx --type api` |
| 2 事前チェック | 機械で分かる不足を先に潰す | `harness precheck` |
| 3 AIレビュー | 5つのロールの順に、チェックリストで確かめる | Copilot Chatで `/review` |
| 4 形式チェック | レビュー結果の形式を確かめる | `harness lint` |
| 5 トリアージ | 指摘ごとに採択・不採択を選ぶ | `harness dashboard` |
| 6 蓄積 | 判定を記録し、観点ごとの採択率を出す | `harness triage` → `harness accumulate` |
| 7 育てる | 誤指摘の多い観点を直し、新しい観点を足す | Copilot Chatで `/review-improve` |

1〜4が普通のAIレビューで、5〜7が「育てる」部分です。順番に見ていきます。

## 観点は1つのYAMLファイルで管理する

観点（チェックリスト）の正は、`config/checks.yaml` の1ファイルです。人が読むチェックリストは、ここから生成します。1つの観点は、こんな形で書きます。

```yaml
  - id: ALL-003
    types: [all]
    role: spec_manager
    category: 記載の明確さ
    severity: MUST
    title: 「など」「適宜」「必要に応じて」で範囲がぼかされていない
    viewpoint: 処理対象・条件・値の範囲が列挙または条件式で確定している
    invalid_when: 例示であることが明記され、確定した一覧が別の箇所にある場合
```

大事な項目が2つあります。

**`invalid_when`（無効となるケース）**
この観点を当てはめてはいけない場面です。AIは、これに当たる場合は指摘しません。誤指摘を減らすための一番の道具です。

**`id`**
一度付けたIDは変えません。採択率の履歴が、IDに紐づいているからです。

## 手順1〜4：AIにレビューさせる

### 機械で分かることは先に潰す

AIに見せる前に、`harness precheck` で機械的に確かめられる不足を潰します。文書IDなどの必須項目、必須の見出し、表の列などです。機械で分かることをAIに探させるのは、時間の無駄だからです。

### 5つのロールの視点で見る

`/review` では、AIに5つのロールを順番に演じさせます。

| ロール | 主に見るところ |
| --- | --- |
| アーキテクト | 責務分担、方式、再利用、拡張性 |
| インフラ | 性能、可用性、セキュリティ、ネットワーク |
| 仕様管理 | 業務要件との整合、記載の網羅と一貫性 |
| DBA | テーブル設計、SQL、トランザクション、データ量 |
| 運用 | 監視、ログ、障害時の手順、ジョブ運用 |

一度に全部を見させるより、視点を絞って順番に見させる方が、漏れが少なくなります。

### 指摘のルールを決めておく

`/review` のプロンプトには、指摘の出し方のルールを書いています。

> - 観点ごとに「無効となるケース」に当たらないかを先に確かめ、当たれば指摘しない
> - 根拠（対象のどこを見て、何に照らしたか）を必ず書く。書けない指摘は出さない
> - 書いていないことは「記載が無い」として指摘し、推測で誤りと断定しない。情報が足りなければ Q にする
> - チェックリストに無い問題は check_id を NEW にする

「根拠を書けない指摘は出さない」と「情報が足りなければ質問（Q）にする」は、シリーズの記事「AIに『分からない』と言わせるプロンプト」と同じ考え方です。AIに推測で断定させないことが、誤指摘を減らす近道です。

結果は、表の形でファイルに保存させます。

```markdown
| No | check_id | 重要度 | ロール | 箇所 | 指摘 | 根拠 | 無効となるケースの確認 |
|---|---|---|---|---|---|---|---|
```

形式がそろっていれば、`harness lint` で機械的にチェックでき、後の集計にも使えます。

## 手順5〜6：人が採択・不採択を付けて記録する

`harness dashboard` を実行すると、レビュー結果をまとめたHTMLのダッシュボードができます。人はそこで、指摘ごとに採択・不採択を選びます。

判定は `data/history.jsonl` に1行ずつ記録されます。リポジトリに入っているサンプルの記録は、たとえばこうです。

```json
{"key": "2026-10-02_order-api_result.md#1", "decision": "adopted", "check_id": "ALL-003", "severity": "MUST", "role": "spec_manager", "doc_type": "api", "finding": "「適宜ページングする」では 1 ページの件数と並び順の安定性が決まらない", "triaged_at": "2026-10-02"}
{"key": "2026-10-02_order-api_result.md#4", "decision": "rejected", "check_id": "API-007", "severity": "WANT", "role": "dba", "doc_type": "api", "finding": "参照テーブルと検索条件・使うインデックスが書かれていない", "triaged_at": "2026-10-02"}
```

`harness accumulate` を実行すると、この記録から2つの表が作られます。

### 観点ごとの採択率

```markdown
| check_id | 観点 | 採択 | 不採択 | 採択率 | |
|---|---|---|---|---|---|
| ALL-003 | 「など」「適宜」「必要に応じて」で範囲がぼかされていない | 1 | 0 | 100% |  |
| API-007 | 参照・更新するテーブルと条件が書かれている | 0 | 1 | 0% |  |
```

採択率は「採択 ÷（採択 + 不採択）」です。5件以上の判定がある観点で、採択率が30%未満のものには ⚠ が付きます。件数が少ないうちは判断しないのがポイントです。1〜2件の不採択だけで観点を直すと、たまたまの結果に振り回されます。

### 観点の追加候補

チェックリストに無かった指摘（check_idがNEW）のうち、採択されたものが一覧になります。

```markdown
| 指摘 | 種別 | ロール | 重要度 | 記録日 |
|---|---|---|---|---|
| from の日付はどのタイムゾーンで判定するか（日付の境界） | api | ops | WANT | 2026-10-02 |
```

AIが観点の外から見つけてきた、価値のある指摘です。繰り返し出てくるなら、観点として取り込みます。

## 手順7：チェックリストを育てる

`/review-improve` を実行すると、AIが改善案を作ります。やることは2つです。

**採択率の低い観点を直す**
不採択になった指摘を読んで、「観点の文」か「無効となるケース」をどう直せば誤指摘が減るかを提案させます。多くの場合、`invalid_when` を具体的にするのが効きます。

**追加候補を観点にする**
似た指摘をまとめて、新しい観点の案（id、種別、ロール、重要度、観点、無効となるケース）を作らせます。

どちらも、AIが直接書き換えるのではなく、案を見せて人が了承してから `config/checks.yaml` を直します。変更はPRで出してレビューします。観点の変更も、コードと同じように履歴とレビューを残すわけです。

## 始め方

1. [office-review](https://github.com/shoyo-maya-bot/office-review) をcloneする
2. Windowsなら `setup.cmd` をダブルクリック、macOS・Linuxなら `./setup.sh` を実行する
3. VS Codeでフォルダを開き、Copilot Chatで次のように入力する

> /review inputs/api/order-api.md

同梱のサンプルで、レビュー結果の表が作られます。慣れてきたら、自分たちの設計書と観点に置き換えていきましょう。実案件の観点は、会社のGitHubに複製してから足していく想定です。

## よくある失敗

**最初から完璧なチェックリストを作ろうとする**
観点を考えるのに時間をかけすぎて、レビューが始まらないのはよくある失敗です。一般的な観点で始めて、実際の結果から育てる方が早く良くなります。

**不採択を記録しない**
「違う」と思った指摘を黙って捨てると、何も学習されません。採択だけでなく、不採択も記録することで、誤指摘の多い観点が見えてきます。

**件数が少ないうちに観点を直す**
1〜2件の不採択で観点を変えると、たまたまの結果に振り回されます。ある程度の件数がたまってから判断しましょう。

**観点のIDを付け直す**
整理したくなってIDを振り直すと、それまでの採択率の履歴がつながらなくなります。一度付けたIDは変えず、使わない観点は残したままにしておきます。

## まとめ

AIレビューの精度は、チェックリストの質で決まります。そしてチェックリストは、使いながら育てるものです。

- 観点に「無効となるケース」を書いて、誤指摘を減らす
- 人の採択・不採択を記録して、採択率で観点を見直す
- AIが見つけた新しい指摘を、次の観点として取り込む

AIの指摘を「当たり」「外れ」で終わらせず、次のレビューの材料にしていく。それが、AIレビューを使い続けるためのコツです。
