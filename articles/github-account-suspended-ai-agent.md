AIエージェントに GitHub の作業を任せていたら、ある日アカウントが凍結（停止）されました。

この記事では、何が起きたのか、どう申し立てたのか、そして同じことを起こさないために何を変えるのかをまとめます。
AIエージェントに「全部やっておいて」と頼み始めた人に、先に知っておいてほしい話です。

:::message
凍結は、申し立てから 6 日後に解除されました。
どの規約に当たったのかは、最後まで具体的には知らされていないので、原因の部分は推測です。
:::

## 何が起きたか

### やっていたこと

自分の公開リポジトリ 15 個を、AIエージェント（Claude Code）に直してもらっていました。
内容は、バグの修正、テストの追加、ドキュメントの手直しなどです。
直した結果を別の AI に採点してもらい、点数が上がるまで直す、という流れを何周も回していました。

AIエージェントは、作業を小さく分けて「サブエージェント」に配ることができます。
今回は、リポジトリごとにサブエージェントを 1 つずつ割り当て、15 個を同時に動かしていました。
それぞれが修正を push し、PR（プルリクエスト）を作り、CI（自動テスト）の結果を確認します。

### 1 日で起きていたこと

振り返ると、1 日のうちに次のようなことが起きていました。

- PR を 50 本ほど作成
- それぞれの PR に何度も push
- CI の結果を、数十秒おきに API で確認
- 落ちた CI の再実行

どれも自分のリポジトリの中での作業です。
人に迷惑をかけるつもりはまったくありませんでした。
ただ、人間の手作業ではありえない量と速さだったのは確かです。

### 突然の 403

修正の 5 周目を進めている途中で、GitHub の API がすべて次のエラーを返すようになりました。

```text
HTTP 403 "Sorry. Your account was suspended"
```

ブラウザでアカウントを開くと、こう表示されていました。

> Access to your account has been suspended due to a violation of our Terms of Service.

「利用規約（Terms of Service）に違反したため、アカウントを停止しました」という意味です。
どの規約に違反したのかは書かれていません。

## 凍結から申し立てまでの時系列

日付と時刻は日本時間です。

| 日時 | できごと |
| --- | --- |
| 10/8（木）昼〜深夜 | AIエージェントで 15 リポジトリの修正を何周も回す。PR は 1 日で 50 本ほど |
| 10/9（金）0 時台 | 5 周目の途中で、GitHub の API がすべて 403 を返すようになる |
| 10/9（金）1 時ごろ | サインインを試すと「サインインの失敗が続いている」と表示され、しばらく入れなくなる |
| 10/9（金）9 時ごろ | 改めてサインインし、「Account suspended」の画面を確認 |
| 10/9（金）9 時台 | 復旧の申し立てを送信。チケット番号付きの自動返信が届く |
| 10/9（金）10 時ごろ | GitHub を使う定期タスクを一時停止 |
| 10/9（金）13 時台 | サポートの担当者から「GitHub をどう使う予定か教えてほしい」と返信。使い方と今後の対策を英語で返信 |
| 10/15（木）6 時台 | 「制限を解除しました」とサポートから連絡があり、凍結が解除される |

凍結されていた期間は、およそ 6 日間でした。
凍結に気づいてから申し立てを送るまでには、半日ほどかかりました。
夜中に気づいたこと、サインインの制限がかかったこと、申し立てのフォームを探すのに手間取ったことが理由です。

GitHub は、審査にかかる日数を公表していません。
利用者の報告を見ると、数日で戻った人もいれば、数週間かかった人もいるようです。
凍結中は、そのアカウントでは何もできないと考えておいたほうがよさそうです。
今回は、間に週末をはさんで 6 日間でした。

## 凍結されると何が困るか

凍結されると、そのアカウントでは何もできなくなります。
思っていたより影響は広く、次のものがまとめて止まりました。

- **リポジトリと PR**：外から見えなくなりました。消えたわけではなく、凍結されている状態です。
- **GitHub Pages のサイト**：同じアカウントで公開していたサイトも見られなくなりました。
- **Zenn の記事更新**：Zenn を GitHub のリポジトリと連携していたので、記事の追加や修正ができなくなりました。
- **定期実行のタスク**：GitHub を使う自動タスクは、毎回失敗するようになりました。

1 つのアカウントに色々なものを載せていると、止まったときに全部が一緒に止まります。
これは今回いちばん実感したことです。

## 原因として考えられること

GitHub の規約には、自動化についての決まりがあります。
「Acceptable Use Policies（利用規定）」には、禁止事項として次のような項目があります。

- 過度な自動の大量の活動（excessive automated bulk activity）
- 自動的な手段でサーバーに過度な負担をかけること（undue burden on our servers through automated means）

今回の作業は、自分のリポジトリだけを対象にした、まじめな修正でした。
それでも、短時間に大量の PR と push と API 呼び出しを繰り返したので、機械的には「過度な自動の大量の活動」に見えた可能性があります。

もう 1 つ考えられるのが、アカウントの持ち方です。
GitHub の利用規約では、無料のアカウントは 1 人 1 つまでとされています。
ただし、自動化専用の「マシンアカウント」は、個人アカウントとは別に 1 つだけ持てます。
自動化用に別アカウントを作っている場合は、この決まりに沿っているかを確認しておくと安心です。

## 申し立ての手順

凍結の画面にある「contact support」から、サポートに連絡できます。
実際にやった手順は次のとおりです。

1. 復旧の申し立て専用のフォーム（GitHub の公式ページ「GitHub Appeal and Reinstatement」から開けます）を開きます。
2. サインインできない場合は、先に「サインインできない」窓口でメールアドレスを確認します。
3. 申し立ての種類を選びます。
4. 何をしていたのかを正直に書いて送ります。

申し立てには 2 種類あります。

- **Reinstatement（復旧）**：指摘された点を直すので、元に戻してほしいという申し立て
- **Appeal（異議）**：違反はしていない、と反論する申し立て

今回は、量が多すぎたことに心当たりがあったので「復旧」を選びました。
本文には、次のことを英語で書きました。

- 自分のリポジトリの修正に、AIエージェントを使っていたこと
- 他人のリポジトリには何も書き込んでいないこと
- 短時間の大量の操作が、乱用に見えたかもしれないこと
- 今後は量と速さを抑えること

送ると、すぐにチケット番号付きの自動返信が届きました。
サポートが混んでいるので時間がかかる、という内容です。
同じ申し立てを何度も送ると、かえって遅くなることがあります。
追加の情報は、届いたメールへの返信で送ります。

数時間後、担当者から「GitHub をどのように使う予定か教えてほしい」という返信が来ました。
不正利用を検知する仕組みに引っかかったので、人の手で確認している、という説明も添えられていました。

そこで、次のことを答えました。

- 個人の開発者で、汎用の開発ツールを公開リポジトリで作っていること
- Zenn のブログと、小さな静的サイトもこのアカウントで公開していること
- AIエージェントは自分のリポジトリだけを操作し、PR のマージは自分で判断していること
- 一度に動かしすぎたことへのお詫びと、今後の具体的な上限
- 使っている GitHub アカウントはこれ 1 つだけであること

その 5 日後に「制限を解除しました」という連絡が来て、元どおり使えるようになりました。
「使い方」を聞かれたら、何のためのアカウントで、どう自動化していて、今後どう抑えるのかを具体的に答えるのがよさそうです。

:::message alert
凍結中に別のアカウントを作って同じ作業を続けるのは、やめておきましょう。
凍結の回避とみなされると、解除がさらに難しくなるおそれがあります。
:::

## 再発防止策

ここからが本題です。
AIエージェントに GitHub を任せるときのルールを、次のように変えることにしました。
GitHub の公式ドキュメント「REST API を使うためのベストプラクティス」にある推奨も取り入れています。

### 1. 同時に動かすのは 2 つまで

公式ドキュメントでは、API のリクエストは同時ではなく「順番に」送ることがすすめられています。
今回は 15 個のサブエージェントを同時に動かしていました。
GitHub に書き込む作業を同時に動かすのは、最大 2 つまでにします。

### 2. push は「テストが通ってから 1 回」

AIエージェントは、直すたびに push して CI で確かめようとしがちです。
これをやめて、手元でテストと lint が通ってから、まとめて 1 回だけ push するようにします。
CI の回数が減るので、GitHub の負担も、自分の待ち時間も減ります。

### 3. 書き込みには間隔をあける

公式ドキュメントでは、POST や PUT などの書き込みを続けて送るときは、1 秒以上あけることがすすめられています。
さらに余裕を持たせて、次のように決めました。

- PR の作成は 1 分以上あける
- 1 日の上限は PR 10 本、push 30 回まで
- 上限を超えそうなら、翌日に回す

### 4. CI の結果は「通知」で待つ

CI の結果を数十秒おきに API で確かめるのは、負担の大きいやり方です。
公式ドキュメントでも、ポーリング（何度も聞きに行くこと）より、Webhook などの通知を使うことがすすめられています。
通知で待てるときは通知で待ち、どうしても確かめるときは 2 分以上あけます。

### 5. エラーが出たら、すぐ止める

GitHub は、使いすぎると「secondary rate limit（二次的な制限）」というエラーを返すことがあります。
AIエージェントは、エラーが出ると「直そう」として再試行を重ねがちです。
ここで粘ると、状況が悪くなります。

指示ファイルには、次のように書いておきます。

> 403・429・「secondary rate limit」が出たら、再試行せずにすぐ作業を止めて報告してください。

### 6. 作業を数日に分ける

15 リポジトリを 1 日で直すのをやめて、1 日 3〜5 リポジトリずつに分けます。
急ぐ理由がない作業なら、ゆっくり進めても困ることはありません。

### 7. 1 つのアカウントに全部を載せない

今回は、ツールのリポジトリも、ブログ（Zenn）も、謎解きサイトも、同じアカウントに載せていました。
止まったときの影響を小さくするために、大事なものはどこに置くかを見直します。

## AIエージェントへの指示の例

最後に、AIエージェント向けの指示ファイル（AGENTS.md や CLAUDE.md など）に入れるルールの例です。
そのまま使える形にしてあります。

```markdown
## GitHub の使い方の上限
- GitHub に書き込む作業（push・PR・CI の再実行）は、同時に 2 つまで。リポジトリは順番に処理する。
- push は、手元でテストと lint が通ってから、1 つの PR につき原則 1 回。
- PR の作成は 1 分以上あける。1 日の上限は PR 10 本・push 30 回。
- CI の結果を確かめるときは、2 分以上あける。
- CI の再実行は、1 つのジョブにつき 1 回まで。
- 403・429・「secondary rate limit」が出たら、再試行せずにすぐ止めて報告する。
```

## まとめ

- AIエージェントは、人間ではありえない量と速さで GitHub を操作できます。
- 自分のリポジトリだけの作業でも、量が多すぎると規約違反とみなされることがあります。
- 凍結されると、リポジトリだけでなく、連携しているサービスもまとめて止まります。
- 「同時に動かす数」「push の回数」「書き込みの間隔」「エラーで止まる」を指示ファイルで決めておきましょう。

AIエージェントに任せるのは、とても便利です。
ただ、任せる範囲と一緒に「速さの上限」も決めておく必要がありました。
解除されたあとは、この記事の再発防止策を守って、少しずつ作業を再開しています。
