Word・Excel・PDFの設計書をMarkdownにしておくと、Gitで差分を管理でき、AIにもそのまま読ませられます。このシリーズでも、何度か「仕様書のMarkdown化はAIへの良いinputになる」と書いてきました。

ただ、変換には落とし穴があります。**変換の途中で内容が抜け落ちても、見た目では気づきにくい**のです。抜け落ちた設計書をAIに読ませれば、AIは抜けた部分を推測で埋めてしまいます。

この記事では、変換で欠けた内容を機械で検知する仕組みと、AIに読ませるための出力の工夫を紹介します。実物は [doc-to-markdown](https://github.com/shoyo-maya-bot/doc-to-markdown)（コマンド名 `doc2md`）で公開しています。サンプルの文書はすべて架空です。

## どんな内容が抜け落ちるのか

実務の文書には、Markdownに素直に変換しにくい要素がたくさんあります。

- **Excel**：セル結合、2段の見出し、1シートに複数の表、非表示の行やシート、計算結果が保存されていない数式
- **Word**：テキストボックス、脚注、コメント、変更履歴、ヘッダー・フッター
- **PowerPoint**：SmartArtの文字、発表者ノート
- **PDF**：2段組み、毎ページ繰り返すヘッダー、スキャンした画像のページ

変換ツールが対応していない要素は、エラーにならずに静かに消えることがあります。これが一番やっかいです。

## 変換ロスを2段構えで検知する

`doc2md` は、変換のたびに「欠けていないか」を2つの方法で確かめます。

### 1. 構造の数を比べる

変換の途中で認識した見出し・箇条書き・表・表の行・画像の数と、出力されたMarkdownの中の数を比べます。整形の途中で落ちたものがあれば、ここで分かります。

### 2. 本文の文字数を、別の経路で数えて比べる

こちらが肝心です。元のファイルから、**変換とは別の方法で**文字数を直接数えます。

| 形式 | 数え方 |
| --- | --- |
| Word / PowerPoint | ファイルの中のXMLにある全テキスト |
| Excel | 全セル |
| PDF | 全文字 |

この文字数と、出力の文字数を比べます。変換ツールが対応していない要素（図形の中の文字など）は、変換の経路では見えません。でも別の経路で数えれば、「元には文字があるのに、出力には出ていない」ことが分かります。

### 警告の種類

検知した結果は、警告としてレポートに出ます。

| rule_id | 意味 | 対応 |
| --- | --- | --- |
| `loss.headings` / `loss.tables` / `loss.table_rows` など | 認識した要素より出力が少ない | 目視で確認する |
| `loss.text` | 本文の文字数が、認識した量の95%未満 | 目視で確認する |
| `loss.raw_text` | 元ファイルから直接数えた文字の95%未満しか出力されていない | 図形・グラフなどを確認し、`--via-pdf` の結果と比べる |
| `convert.warning` | 未確定の変更履歴、非表示の行、計算結果の無い数式、OCRしたページなど | 内容を確認する |

警告があっても、終了コードは0（成功）のままです。CIなどで警告も失敗扱いにしたいときは、`--strict` を付けます。

## 使い方

### 基本の変換

```bash
doc2md 仕様書.docx -d out/                          # out/仕様書.md と out/仕様書.assets/
doc2md docs/ -d out/ -r --continue-on-error         # フォルダ一括（1 ファイル失敗しても続行）
doc2md 台帳.xlsx -d out/ --skip-hidden --recalc      # 非表示を除く・数式を再計算
doc2md 規程.docx -d out/ --track-changes show        # 変更履歴を表示
doc2md 報告書.pdf -d out/ -f json -o report.json     # 変換レポートを JSON で
```

`-f json` を付けると、警告の一覧を機械で読める形で受け取れます。AIエージェントやCIから使うときは、こちらが便利です。

### 欠けていたときの調べ方

`loss.raw_text` が出たら、レイアウトを優先した変換と比べてみます。

```bash
doc2md 設計書.docx -d out/normal -f json
doc2md 設計書.docx -d out/via-pdf --via-pdf -f json
```

`--via-pdf` は、LibreOfficeで一度PDFにしてから文字を取り出す方法です。図形の中の文字など、通常の変換で拾えないものが出てくることがあります。2つの結果を比べて、片方にしか無い段落や表を探します。

この比較は、Copilot Chatのプロンプト `/doc2md-investigate-loss` で任せることもできます。2通りの変換を実行し、欠けている内容と原因の候補、どちらの結果を使うべきか、原本のどこを目で確かめるべきかを報告させます。

## AIに読ませるための出力

### Front Matterで「元の設計書が更新されたか」を検知する

```bash
doc2md 設計書/ -d out/ -r --front-matter --llms-txt
```

`--front-matter` を付けると、各Markdownの先頭に次の情報が入ります。

- `title`、`id`（人が付ける識別子。再変換しても引き継がれる）
- `source`（元のファイル）
- `source_sha256`（元ファイルの内容のハッシュ）
- `generator`

`source_sha256` があると、「元の設計書は更新されたのに、Markdownが古いまま」という状態を検知できます。AIが古い設計書を読んで作業するのを防げます。

### llms.txtで資料一式を渡す

`--llms-txt` を付けると、出力先に2つのファイルができます。

- `llms.txt`：文書の一覧
- `llms-full.txt`：全文を1ファイルにつなげたもの

AIに「この資料一式を前提に答えて」と頼むときに、まとめて渡せます。

### 図は画像ではなく、編集できる形で

業務フローなどの図は、画像のままだとAIも人も中身を扱いにくいです。`doc2md` には、箱と矢印をYAMLで書いてdraw.ioのファイルを作る `figspec` も入っています。AIに図を描かせるときも、この形式で出させれば、人がdraw.ioで手直しでき、Gitで差分も追えます。

## 移行は小さなロットで進める

既存の設計書をMarkdownに移すときは、一度に全部をやらないのがコツです。リポジトリの移行ガイドでは、次のように進めています。

1. 同じ種類の文書を10〜20件選ぶ
2. `--dry-run` で、読み方と必要なソフトを確認する
3. `--front-matter --llms-txt -f json` で変換する
4. レポートの `loss.*` を全件確認する。欠けていれば `--via-pdf` で再変換して見比べる
5. 図はfigspecかdraw.ioで作り直す（画像のままにしない）
6. 人が原本と突き合わせて、レビューで承認する
7. 承認されたら、Markdownを正本にする。原本は参照用として保管する

表と文章が中心の文書（API定義・バッチ定義など）から始めて、図が中心の文書は後に回すのがおすすめです。

### 人の突き合わせで見るところ

機械の検知だけでは、すべては分かりません。最後は人が原本と見比べます。ガイドのチェックリストから抜粋します。

- 見出しの数と順番が原本と同じ
- 表の行数・列数が原本と同じ。結合セル・2段見出しの意味が崩れていない
- 注記（※）・欄外の補足・コメント・変更履歴が残っている（必要なら）
- 図の要素と接続（矢印の向き・ラベル）が原本と同じ
- 数値・日付・コード値が原本と一致（抜き取りで10箇所）
- AIに必要な情報（パラメータファイル名・メッセージID・テーブル名）が明記されている

最後の項目が大事です。Markdown化は、AIが必要とする情報が書かれているかを見直す良い機会でもあります。

## 分かっている制限

便利な道具ですが、何でも変換できるわけではありません。

- PDFの見出し・段落の区切りは推定です。3段組みなどの複雑なレイアウトは崩れることがあります
- 画像の中の文字（図・スクリーンショット）はOCRしません（スキャンしたページ全体のみ）
- Excelのグラフ・図形、PowerPointのグラフは、文字だけが対象です
- 「方眼紙」形式のExcel（帳票レイアウト）は表として認識されず、段落の並びになります

制限を知っておけば、どこを人が確かめるべきかも分かります。

## よくある失敗

**変換結果を確かめずにAIに渡す**
抜け落ちた設計書を読んだAIは、抜けた部分を推測で埋めます。変換レポートの警告は、必ず確認してから使いましょう。

**元の設計書だけ更新して、Markdownが古いまま**
原本とMarkdownの両方を正としていると、どちらが最新か分からなくなります。移行中は原本を正にし、終わったらMarkdownを正に切り替えます。`source_sha256` で古さを検知できるようにしておきましょう。

**変換結果をそのままコミットする**
機密を含む文書のテキスト版が、うっかりGitHubに上がることがあります。変換結果の置き場所は `.gitignore` に入れ、正本にすると決めたものだけを管理しましょう。

**一度に全部を移そうとする**
数百の文書を一気に変換すると、確認が追いつきません。種類ごとの小さなロットで、変換と確認をセットで進めます。

## まとめ

設計書のMarkdown化は、AIを活用するための土台づくりです。ただし、変換で欠けた設計書は、かえってAIを間違わせます。

- 構造の数と、別の経路で数えた文字数で、変換ロスを機械で検知する
- 元ファイルのハッシュで、Markdownが古くなったことに気づけるようにする
- 小さなロットで移し、最後は人が原本と突き合わせる

「Markdownにしたから大丈夫」ではなく、「Markdownにしたものを確かめたから大丈夫」にしていきましょう。
