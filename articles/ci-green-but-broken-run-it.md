AIにコードを書かせて、テストも書かせて、CIも緑。これで安心、と思っていませんか。

この記事では、AIと一緒に作った業務効率化ツール群（15リポジトリ）を総点検したときに見つかった不具合を紹介します。ほとんどが**CIが緑のまま**残っていた不具合でした。そのうえで、どんなCIを足せば拾えるようになったかをまとめます。

題材のリポジトリは [shoyo-maya-bot](https://github.com/shoyo-maya-bot) で公開しています。特定の会社やシステムの名前を含まない汎用版です。

## 結論：CIは「書いたテスト」しか確かめない

先に結論です。

- 見つかった不具合は、どれも**CIがそもそも動かしていないところ**にありました。
- 具体的には「Windowsで動かす」「アプリを起動して本物のDBにつなぐ」「同じ名前のファイルが2つある」「途中で落ちる」といった場面です。
- AIが書いたテストは、AIが想定した場面しか確かめません。想定の外は、緑のまま素通りします。

「CIが緑＝動く」ではなく、「CIが緑＝CIが確かめた範囲は動く」です。範囲を広げるには、**実際に動かすジョブ**を足すしかありません。

## 見つかった不具合（CIは緑だった）

### データを黙って壊すもの

いちばん怖いのは、エラーにならずに結果だけが間違うものです。終了コードが0なので、使う人も気づけません。

| ツール | 起きていたこと | なぜCIで拾えなかったか |
| --- | --- | --- |
| 設計書をMarkdownにする変換ツール | `spec.docx` と `spec.xlsx` を同時に変換すると、後のファイルが前の出力を上書きする | テストは1ファイルずつしか変換していなかった |
| 設計書の差分ツール | 見出しが2段（「型情報」の下に「型」「桁」）の表で、2段目をデータ行として読む。桁を50→60に変えても差分0件 | テスト用の表がすべて1段の見出しだった |
| 品質データの分析ツール | 外部のAIに送る前の伏せ字が「本文」の列にしか効かず、成果物名・全角のメールアドレス・区切りなしの電話番号が素通り | 伏せ字のテストが半角の例しか使っていなかった |
| 共通のHTTPクライアント | 503やタイムアウトのとき、POSTも再送する。サーバーには4回届き、通知や課題が重複する | テストは「再試行すること」は確かめても「何回届いたか」は見ていなかった |
| Officeの一括置換ツール | ファイル名の置換で「置換後」に `../../` を書くと、出力フォルダの外にファイルができる | 置換後の値の検査が無く、テストにも悪い値が無かった |

どれも、直す前に「失敗する再現テスト」を書いてから直しました。たとえば重複送信は、手元で小さなHTTPサーバーを立てて「POSTが何回届いたか」を数えるテストにしています。

```python
def test_post_5xx_is_sent_once(self):
    with LocalServer(status=503) as s, self.assertRaises(HttpError) as cm:
        _client(s.url).post("messages", json_body={"text": "hi"})
    self.assertEqual(cm.exception.status, 503)
    self.assertEqual(s.hits, ["POST"])  # 修正前は ["POST", "POST", "POST", "POST"]
```

「再試行するか」ではなく「相手に何回届いたか」を確かめるのがポイントです。

### Windowsで止まるもの

利用者のPCはWindowsなのに、CIはLinuxだけでした。Windowsの実機で環境構築を通しで試したところ、次のようなものが見つかりました。

- Java 8が入っているPCで、バージョン判定がJava 17と誤判定する
- セットアップのスクリプトが確認画面で止まり、そのまま待ち続ける
- PythonがWindowsの既定の文字コード（cp1252）で出力し、日本語の完了メッセージを書けずに落ちる

最後のものは、CIにWindowsのジョブを足した最初の実行で見つかりました。手元のLinuxでは絶対に再現しない種類です。

### 「動かしていない」もの

サンプルのSpring Bootアプリでは、CIが `./gradlew build` で単体テストを流していました。しかし次のものは、CIで一度も動いていませんでした。

- アプリを起動して、本物のPostgreSQLにつなぐこと
- Karateで書いたAPIのテスト（アプリが起動している前提なので、通常のテストから外していた）
- DBが止まったときの応答（503を返すはずが、500になっていた）

### 途中で落ちたときに壊れるもの

AWSとAzureで動かすレビュー基盤（キューとワーカーの構成）も、テストは緑でした。別のAIに独立してレビューさせたところ、次の問題が見つかりました。

- **ジョブが永久に「処理中」になる。** SQSの「何回受け取ったらDLQ（退避用のキュー）へ移すか」と、ワーカーの「何回失敗したら失敗にするか」が同じ3回でした。3回目の途中でワーカーが止まると、ワーカーが失敗にする前にSQSがメッセージを退避します。ジョブは「処理中」のまま残ります。
- **同じジョブを2台が同時に処理する。** 状態の更新が「今の状態が処理中なら」という条件だけで、処理中→処理中の更新が常に通っていました。AIの費用も2倍になります。
- **大きなファイルの上限が効かない。** `Content-Length` を見て断っていましたが、chunked形式で送られると最後まで受け取ってから検査していました。

どれも「正常に動く」テストでは出てきません。「途中で落ちる」「同時に来る」「ヘッダが無い」を、わざと起こすテストが要ります。

## 足したCI：動かして確かめる

ここからは、上の不具合を拾えるようにするために足したCIです。GitHub Actionsは公開リポジトリなら無料で使えます。

### 1. アプリを起動して、外から叩く

サンプルアプリのリポジトリに、e2eのジョブを足しました。やっていることは次のとおりです。

1. docker composeでPostgreSQLとS3の代わりを起動する
2. アプリのjarを作って起動する
3. curlで正常系とエラー系（200・201・400・404・409）を確かめる
4. Karateのテストを流す。**0件しか動かなかったら失敗にする**
5. DBのコンテナを止めて、503とエラーコードが返ることを確かめる
6. DBを戻して、再起動なしで200に戻ることを確かめる

4の「0件なら失敗」は大事です。タグの指定を間違えると、テストが1件も動かないまま緑になるからです。

```bash
# Karate の結果（JUnit XML）にテストが 1 件以上あり、失敗が無いことを確かめる
tests=0; failures=0
for f in "$dir"/*.xml; do
  t=$(grep -o '<testsuite [^>]*' "$f" | sed -nE 's/.* tests="([0-9]+)".*/\1/p' | head -1)
  e=$(grep -o '<testsuite [^>]*' "$f" | sed -nE 's/.* failures="([0-9]+)".*/\1/p' | head -1)
  tests=$((tests + ${t:-0})); failures=$((failures + ${e:-0}))
done
[ "$tests" -gt 0 ] || { echo "::error::Karate のテストが 1 件も実行されていません"; exit 1; }
[ "$failures" -eq 0 ] || { echo "::error::Karate のテストが $failures 件失敗しました"; exit 1; }
```

### 2. Windowsのランナーで入口を通しで動かす

セットアップ用のリポジトリに、`windows-latest` のジョブを足しました。

- `.cmd` と `.ps1` が、チェックアウト後もCRLFのままか
- PSScriptAnalyzerで、PowerShellのスクリプトに警告が無いか
- 前提ツールの確認（`-Check`）と、実際には入れない試し実行（`-DryRun`）が、確認画面で止まらずに終わるか
- `setup.cmd` でツールを2つcloneし、仮想環境に入れ、`--help` が動くか
- もう一度実行して、更新（pull）の道も通るか

確認画面で止まらないように、`CI` という環境変数があるときは確認を飛ばす作りにしました。GitHub Actionsは `CI=true` を自動で設定します。

```bat
if not defined CI if not defined DEVTOOLS_NO_PAUSE pause
```

### 3. 学習用の「修正前のコード」も毎週ビルドする

サンプルアプリには、教材の演習で使う「わざと弱いところを残したブランチ」があります。mainだけをCIで回していると、こちらが静かに壊れても気づけません。

そこで、mainに置いたワークフローから `ref: exercise-base` でチェックアウトして、毎週ビルドするようにしました。さらに、**演習で見つけてほしい弱いところが、まだ残っていること**も確かめます。だれかがうっかり直すと、教材と合わなくなるからです。

### 4. わざと壊すテスト

レビュー基盤では、壊れ方のテストを1つのファイルにまとめました。

- 処理中のジョブに重複したメッセージが届いても、2回処理しない
- 前のワーカーが落ちて時間が経ったジョブは、別のワーカーが引き継ぐ
- 再試行をまたいで費用を足し上げ、残りの予算だけを次の試行に渡す
- chunkedで送られた大きな本文を、上限の時点で読むのをやめて413を返す
- キューへの送信に失敗したジョブを「待ち」のまま残さない

このテストはクラウドのエミュレーター（AWSはmoto、AzureはAzurite）にも同じものを流しています。

## よくある失敗

**AIにテストを書かせて満足する。** AIは、自分が書いたコードの「うまくいく道」のテストを書くのが得意です。壊れ方のテストは、こちらから「同時に来たら？」「途中で落ちたら？」「Windowsだったら？」と聞かないと出てきません。

**同じAIに採点させる。** 今回の不具合の多くは、作ったのとは別のAIにレビューさせて見つかりました。作り手と採点役が同じだと、見落としも同じになります。

**テストが0件でも緑になる。** タグや対象の指定ミスで、テストが1件も動かないことがあります。件数が0なら失敗にする一行を入れておきましょう。

**利用者の環境でCIを回していない。** 利用者がWindowsなら、Windowsのランナーで入口のスクリプトを動かすだけで、かなりの不具合が拾えます。

## まとめ

- CIが緑でも、CIが動かしていないところは何も保証されません。
- 見つかった不具合は「複数のファイル」「2段の見出し」「全角」「再送」「Windows」「途中で落ちる」「同時に来る」と、どれも**普通の使い方の少し外**にありました。
- 足すべきは、アプリを起動して外から叩くジョブ、利用者と同じOSのジョブ、わざと壊すテストです。
- AIに頼むときは「壊れ方のテストも書いて」と、はっきり頼みましょう。
