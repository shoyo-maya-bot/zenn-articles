チャット画面にコードを貼り、返ってきた回答をコピーしてエディタに戻す。エラーが出たら、またそのエラーを貼り付ける。AIを使うとき、こんな往復をしていないでしょうか。

この往復で、人間がやっているのは「中継役」です。エージェント型のAIを使うと、この中継役から解放されます。

## 会話型とエージェント型の違い

|  | 会話型 | エージェント型 |
| --- | --- | --- |
| ファイルを読む | 人が貼り付ける | AIが自分で開いて読む |
| コードを書く | 回答を人がコピーする | AIが直接ファイルを編集する |
| 実行・テスト | 人が実行して結果を貼る | AIがコマンドを実行して結果を見る |
| エラー対応 | 人がエラーを貼り直す | AIが自分で読んで直す |
| 人の役割 | 中継役 | 指示とレビュー |

代表的なものに、Claude CodeやGitHub Copilotのエージェント機能などがあります。

ちなみに、Claude OpusのようなAIモデルそのものがエージェントなのではありません。モデルに「ファイル操作」や「コマンド実行」などの道具を持たせる仕組みがあって、初めてエージェントとして動きます。この仕組みは「ハーネス」と呼ばれ、別の記事で詳しく書いています。

## 実際の動きを比べてみる

単体テストを書いてもらう場面で比べてみましょう。

**会話型の場合**

1. テストしたい関数のコードをコピーして、チャットに貼る
2. 「この関数の単体テストを書いて」と頼む
3. 返ってきたテストコードをコピーして、ファイルに貼る
4. テストを実行する。import のパスが違ってエラーになる
5. エラーをコピーしてチャットに貼る
6. 修正版をコピーして、また貼る。今度は1件だけテストが失敗する
7. 失敗内容を貼って、また直してもらう

人間は、コピーと貼り付けを何度も繰り返しています。

**エージェント型の場合**

> src/utils/date.ts の関数に単体テストを書いてください。既存のテストの書き方に合わせて、テストが全部通るまで直してください。

あとは、AIが次のように動きます。

1. 対象のファイルと、既存のテストファイルを自分で読む
2. テストの書き方やフォルダの決まりを真似て、テストを書く
3. テストを実行する。import エラーが出たら、自分で読んで直す
4. 失敗したテストがあれば、テストの間違いか、元のコードのバグかを判断して報告する
5. 全部通ったら、何をしたかをまとめて報告する

人間がやるのは、最初の指示と、最後に変更内容を確認することだけです。

## エージェントに任せると楽になること

- **単体テスト：** テストを書く、実行する、失敗したら直す。ここまでを一気に任せられます。
- **影響範囲の調査：** 「この関数を変えたらどこに影響する？」と聞くと、リポジトリ全体を読んで調べてくれます。
- **ドキュメントのMarkdown化：** 大量の仕様書を、まとめて読みやすい形式に変換できます。

どれも会話型でもできなくはありません。ただ、ファイルの数が増えるほど、コピペの往復が大きな負担になります。

## 最初の一歩

1. **ツールを用意する。** インストールや初期設定の方法はツールによって違い、更新も頻繁です。各ツールの公式ドキュメントの手順に従いましょう。会社で使う場合は、利用が許可されているツールを先に確認します。
2. **作業用のブランチを切る。** Gitで管理されているリポジトリで始めます。何かあっても、ブランチごと捨てれば元通りです。
3. **小さくて、失敗しても戻せる作業を選ぶ。** テストの追加が一番のおすすめです。本体のコードを変えないので、壊れる心配がほとんどありません。
4. **普段チャットで頼むのと同じ日本語で指示する。**
5. **終わったら、変更の差分を必ず自分の目で確認する。**

## 指示のコツ

指示の書き方は、会話型とほとんど変わりません。ただ、次の3つを入れると、エージェントは格段に動きやすくなります。

**範囲を絞る**
「このリポジトリのテストを書いて」ではなく、「src/utils/date.ts の関数のテストを書いて」と対象を指定します。

**完了の条件を書く**
「テストが全部通るまで」「lintのエラーがなくなるまで」など、どうなったら終わりかを伝えます。エージェントはそこに向かって、実行と修正を繰り返します。

**やってほしくないことを書く**
「テスト対象のコードは変更しないでください。バグを見つけたら、直さずに報告してください」のように、触ってほしくない範囲を伝えます。

## よくある不安

**勝手にファイルを壊されない？**
多くのツールには、編集やコマンド実行の前に許可を求める設定があります。最初は毎回承認する設定で使い、Gitでいつでも戻せる状態にしておけば安心です。

**難しそう？**
指示は普通の日本語で大丈夫です。むしろ、コピペの往復がなくなる分、会話型より楽に感じるはずです。

**セキュリティは？**
会社で使う場合は、社内のAI利用ルールや、どのツールが許可されているかを先に確認しましょう。

## よくある失敗

**範囲が広すぎる指示を出す**
「アプリ全体をリファクタリングして」のような大きな指示を出すと、変更が大量になってレビューできなくなります。1回の依頼は、自分が確認しきれる量にしましょう。

**差分を見ずに受け入れる**
エージェントは、頼んでいない箇所まで「ついでに」直すことがあります。どれだけ順調に見えても、変更内容は必ず確認しましょう。

**慣れてきて、承認をすべてオフにする**
毎回の承認が面倒になって、全部を自動で許可したくなります。せめて、ファイルの削除や外部への送信など、取り返しのつかない操作だけは確認を残しておきましょう。

**前提を伝えずに頼む**
エージェントはファイルを読めますが、チームの暗黙のルールまでは知りません。「テストはこのフォルダに置く」「この書き方は禁止」といった決まりは、指示ファイルに書いて伝えましょう。

## まとめ

エージェントは「話し相手」ではなく「作業者」です。人間は中継役をやめ、指示とレビューに集中できます。

会話型で慣れた人ほど、一度触るとその差に驚くと思います。まずは小さなテストの追加から、任せてみてください。
