AIコーディングの広がりとともに、「仕様駆動開発（Spec-Driven Development、SDD）」という言葉をよく聞くようになりました。一方で、昔からある「テスト駆動開発（Test-Driven Development、TDD）」も、AIにコードを書かせる時代に改めて注目されています。

名前が似ていて、どちらも「先に何かを書いてから作る」ので、違いが分かりにくいと感じる人も多いと思います。さらに世の中には、BDD、ATDD、DDD、FDD……と「〇〇駆動開発」がたくさんあります。

この記事では、SDDとTDDの違いを、同じ機能を例にしてできるだけ細かく比べます。そのうえで、ほかの「〇〇駆動開発」も整理し、どう組み合わせればいいかまで解説します。

:::message
SDDを支えるAIツール（Kiro、GitHubのSpec Kitなど）は、更新がとても速い分野です。この記事は2026年10月時点の公式ドキュメントをもとに書いています。コマンド名などの細部は、使う前に公式ドキュメントを確認してください。
:::

## 先に結論

| | 仕様駆動開発（SDD） | テスト駆動開発（TDD） |
| --- | --- | --- |
| ひとことで | 「何を作るか」を先に文章で決め、人とAIで合意してから作る | 「正しく動くか」を先にテストで書き、1歩ずつ作る |
| 最初に書くもの | 仕様書（要件・設計・タスク） | 失敗するテスト |
| 答える問い | 何を、なぜ、どこまで作るか | このコードは期待どおりに動くか |
| 1回の単位 | 機能まるごと（数時間〜数日） | 小さな振る舞い1つ（数分） |
| 主な読み手 | 人とAIの両方（企画・設計・開発） | 開発者と、テストを実行する機械 |

いちばん大事なのは、**SDDとTDDは対立するものではない**ということです。SDDは「何を作るか」を決める手法で、TDDは「決めたものを正しく作る」手法です。担当している範囲が違うので、組み合わせて使えます。

## そもそも「駆動」とは何か

「〇〇駆動開発」の「駆動」は、**開発を前に進めるきっかけと、迷ったときに立ち返る拠り所が何か**を表しています。

- テスト駆動なら、テストが次の一手を決め、テストが「正しさ」の基準になる
- 仕様駆動なら、仕様書が作業を決め、仕様書が「何を作るべきか」の基準になる
- ドメイン駆動なら、業務（ドメイン）の理解が設計を決める

この「何を最初に書き、何を正とするか」という見方で比べると、たくさんある駆動開発の違いが整理しやすくなります。

## この記事で使う例題：送料の計算

違いが分かりやすいように、同じ機能を例にします。ネットショップの送料を計算する機能です。

- 注文の合計金額が5,000円以上なら、送料は無料
- 5,000円未満なら、送料は全国一律600円
- ただし沖縄県への配送は、400円を追加する
- 合計金額が負の数のときはエラーにする

この機能を、TDDとSDDでそれぞれどう作るかを見ていきます。

## テスト駆動開発（TDD）

### 起源と考え方

TDDは、1990年代の終わりに、ケント・ベック（Kent Beck）がエクストリーム・プログラミング（XP）の実践の一つとして広めた手法です。2002年に出た著書『Test-Driven Development: By Example』が原典として知られています（日本語訳は『テスト駆動開発』）。

考え方の中心は、**コードを書く前に、そのコードが満たすべきテストを書く**ことです。そして、ごく小さな歩幅で、次の3つを繰り返します。

1. **Red（レッド）**：次に作りたい振る舞いのテストを1つ書く。まだ実装が無いので、テストは失敗する
2. **Green（グリーン）**：テストが通る最小限のコードを書く
3. **Refactor（リファクタリング）**：テストが通る状態を保ったまま、コードをきれいにする

テストを実行すると、失敗は赤、成功は緑で表示されることが多いので、この名前が付いています。

### 例題をTDDで作る

Node.jsに標準で入っているテストの仕組み（`node:test`）で、実際に動かした手順を紹介します。

**1周目 Red：送料無料のテストを書く**

```js
// shipping.test.js
import { test } from "node:test";
import assert from "node:assert/strict";
import { shippingFee } from "./shipping.js";

test("合計が5,000円以上なら送料は0円", () => {
  assert.equal(shippingFee({ total: 5000, prefecture: "東京都" }), 0);
});
```

関数の中身はまだ空なので、テストは失敗します。

```text
✖ 合計が5,000円以上なら送料は0円
```

ここで「失敗することを確かめる」のが大事です。最初から成功するテストは、何も確かめていない可能性があるからです。

**1周目 Green：とにかく通す**

```js
// shipping.js
export function shippingFee(order) {
  return 0;
}
```

「常に0を返す」は、明らかに手抜きです。でも、TDDではこれで正解です。今あるテストを通す最小限のコードだけを書き、足りない部分は次のテストで明らかにします。

```text
✔ 合計が5,000円以上なら送料は0円
```

**2周目：5,000円未満のテストを足す**

```js
test("合計が5,000円未満なら送料は600円", () => {
  assert.equal(shippingFee({ total: 4999, prefecture: "東京都" }), 600);
});
```

「常に0」では通らないので、ここで初めて条件分岐が必要になります。

```js
export function shippingFee(order) {
  if (order.total >= 5000) return 0;
  return 600;
}
```

境目の4,999円をテストに使っているのがポイントです。境目の値（境界値）は、バグが一番起きやすい場所です。

**3周目：沖縄県のテストを足し、そのあとリファクタリング**

```js
test("沖縄県への5,000円未満の注文は送料1,000円", () => {
  assert.equal(shippingFee({ total: 3000, prefecture: "沖縄県" }), 1000);
});
```

まずは最小限で通します。

```js
export function shippingFee(order) {
  if (order.total >= 5000) return 0;
  if (order.prefecture === "沖縄県") return 1000;
  return 600;
}
```

テストが全部通ったら、リファクタリングです。「1000」がどこから来た数字なのか分かりにくいので、意味のある名前を付けます。

```js
const FREE_SHIPPING_THRESHOLD = 5000; // 送料無料になる合計金額
const BASE_FEE = 600;                 // 全国一律の送料
const REMOTE_SURCHARGE = 400;         // 遠方への追加料金
const REMOTE_PREFECTURES = new Set(["沖縄県"]);

export function shippingFee({ total, prefecture }) {
  if (total >= FREE_SHIPPING_THRESHOLD) return 0;
  const surcharge = REMOTE_PREFECTURES.has(prefecture) ? REMOTE_SURCHARGE : 0;
  return BASE_FEE + surcharge;
}
```

形は大きく変わりましたが、テストは全部通ったままです。これが「テストがあるから、安心して書き直せる」というTDDの強みです。

**4周目：エラーのテストを足す**

```js
test("合計が負の数ならエラーになる", () => {
  assert.throws(() => shippingFee({ total: -1, prefecture: "東京都" }), RangeError);
});
```

失敗を確かめてから、関数の先頭に1行足します。

```js
  if (total < 0) throw new RangeError("合計金額が負の数です");
```

```text
✔ 合計が5,000円以上なら送料は0円
✔ 合計が5,000円未満なら送料は600円
✔ 沖縄県への5,000円未満の注文は送料1,000円
✔ 合計が負の数ならエラーになる
```

4つの振る舞いを、テストという形で1つずつ確かめながら作れました。

### TDDの3つのルール

TDDを実践するうえで、よく言われる約束があります。

- **失敗するテストが無いうちは、本番のコードを書かない**
- **一度に足すテストは1つだけ**
- **テストを通すのに必要な分だけ、コードを書く**

歩幅を小さく保つことで、失敗したときに「何が原因か」がすぐ分かります。

### TDDのよくある誤解

**「テストを先に全部書くこと」ではない**
TDDは、テストを1つ書いては実装する、の繰り返しです。最初に全テストを書き切るのは、TDDとは別のやり方です。

**「テストのための手法」ではない**
TDDで作られたテストは、結果として品質を守ってくれます。ただ、本来の目的は「小さな歩幅で設計を進めること」です。テストを先に書くと、「この関数はどう呼ばれたら使いやすいか」を、使う側の目線で先に考えることになります。

**リファクタリングを飛ばしがち**
マーチン・ファウラー（Martin Fowler）は、TDDの一番よくある失敗として「3つ目のステップ（リファクタリング）を飛ばすこと」を挙げています。テストは通るけれど読みにくいコードが溜まっていきます。

### TDDの向き・不向き

| 向いている | 向いていない（工夫が必要） |
| --- | --- |
| 計算や判定など、入力と出力がはっきりしたロジック | 画面の見た目、デザインの細部 |
| バグを直すとき（まずバグを再現するテストを書く） | 何を作るか自体が決まっていない探索的な試作 |
| 長く保守するコード | 外部サービスに強く依存する部分（差し替えの工夫が必要） |

## 仕様駆動開発（SDD）

### 「仕様駆動」には2つの意味がある

「仕様駆動開発」という言葉は、文脈によって指すものが違うので注意が必要です。

1. **昔からの意味**：仕様を先に書いてから作る、という一般的な考え方。形式的な仕様記述や、後で紹介する「契約による設計」も、仕様を中心にした開発の一種です。
2. **最近の意味（AI時代のSDD）**：AIコーディングエージェントに作業させる前に、要件・設計・タスクを文章で書いて人とAIで合意し、それに沿ってAIに実装させるやり方。

この記事でSDDと呼ぶのは、主に2つ目です。

### なぜ今SDDなのか

会話型のAIに「〇〇を作って」と頼むと、AIはそれらしいコードをすぐ出してくれます。ところが、頼んだ側の頭の中にある前提（対象範囲、例外のとき、制約）が伝わっていないと、AIは推測で穴を埋めます。いわゆる「雰囲気で書いてもらう（vibe coding）」状態です。

SDDは、この推測を減らすために、**作る前に「何を作るか」を文章にして固定する**やり方です。シリーズの記事で「AIの答えがぶれるのはinputが足りないサイン」と書きましたが、SDDはそのinputを最初にそろえる仕組みだと言えます。

### SDDの流れ

ツールによって細部は違いますが、流れはおおむね共通です。

1. **要件（Requirements）**：誰が、何をしたいのか。受け入れ基準（どうなれば完成か）
2. **設計（Design）**：どう作るか。構成、データの形、処理の流れ
3. **タスク（Tasks）**：実装を小さな作業に分けた一覧
4. **実装（Implement）**：タスクを1つずつAIに実装させ、人がレビューする

それぞれの段階で人が内容を確認し、合意してから次へ進むのがポイントです。

### 代表的なツール

**Kiro**
AWSが提供する開発環境です。仕様（Spec）を作ると、`requirements.md`（要件と受け入れ基準）、`design.md`（構成・シーケンス図・実装方針）、`tasks.md`（追跡できる実装計画）の3つのファイルができます。要件の書き方には、後で紹介するEARS記法を使います。

**GitHub Spec Kit**
GitHubが公開しているオープンソースのツールキットです。プロジェクト全体の原則を決める「憲法（constitution）」を最初に作り、そのあと仕様、計画、タスク、実装と進めます。執筆時点のREADMEでは、各段階を `/speckit-constitution`、`/speckit-specify`、`/speckit-plan`、`/speckit-tasks`、`/speckit-implement`、`/speckit-converge` のように呼び出す形になっています（コマンドの名前は版によって変わってきたので、使う前に確認してください）。

### EARS記法：要件を「テストできる文章」にする

SDDで要件を書くときに役立つのが、EARS（Easy Approach to Requirements Syntax）という書き方です。決まった型に当てはめて書くことで、あいまいさを減らします。主な型は次のとおりです。

| 型 | 書き方 | 使う場面 |
| --- | --- | --- |
| 常に | THE SYSTEM SHALL 〜 | いつでも成り立つこと |
| イベント | WHEN 〜 THE SYSTEM SHALL 〜 | 何かが起きたとき |
| 状態 | WHILE 〜 THE SYSTEM SHALL 〜 | ある状態の間 |
| 望ましくない状況 | IF 〜 THEN THE SYSTEM SHALL 〜 | エラーや異常のとき |
| オプション | WHERE 〜 THE SYSTEM SHALL 〜 | ある機能があるとき |

例題の送料計算を、EARSで要件にするとこうなります。

```markdown
# 要件：送料の計算

## ユーザーストーリー
購入者として、注文を確定する前に送料を知りたい。
それによって、送料無料まであといくら買えばよいか判断できるようにしたい。

## 受け入れ基準
1. WHEN 注文の合計金額が5,000円以上である THE SYSTEM SHALL 送料を0円にする
2. WHEN 注文の合計金額が5,000円未満である THE SYSTEM SHALL 送料を600円にする
3. WHEN 合計金額が5,000円未満で、配送先が沖縄県である THE SYSTEM SHALL 送料に400円を加える
4. IF 注文の合計金額が負の数である THEN THE SYSTEM SHALL 注文を受け付けずエラーを返す

## 決まっていないこと
- 離島（沖縄県以外）の扱い
- 送料の消費税の表示方法
```

最後の「決まっていないこと」がとても大事です。SDDの価値の半分は、**作る前に、決まっていないことに気づける**ことにあります。TDDの例では、離島の扱いは誰にも問われないまま実装が進んでいました。

### AIに仕様を書かせるときのプロンプト

ツールを使わなくても、SDDの考え方はAIへの頼み方に取り入れられます。

> 送料を計算する機能を作りたいです。いきなり実装せず、まず requirements.md を書いてください。受け入れ基準はEARS記法（WHEN / IF 〜 THE SYSTEM SHALL 〜）で書き、決まっていないことは推測で埋めずに「決まっていないこと」として一覧にしてください。私が確認してから設計に進みます。

「推測で埋めずに一覧にして」と「確認してから進む」がポイントです。

### SDDの3つのレベル

マーチン・ファウラーのサイトに掲載された、ビルギッタ・ベッケラー（Birgitta Böckeler）による記事では、SDDを仕様の扱い方で3つのレベルに分けています。

| レベル | 仕様の扱い |
| --- | --- |
| spec-first | 作る前に仕様を書く。作り終えたら仕様は使わない |
| spec-anchored | 作り終えたあとも仕様を残し、その後の改修や保守でも使い続ける |
| spec-as-source | 仕様が主なソース。人は仕様だけを編集し、コードには手を触れない |

同じ記事では、Kiroは spec-first 寄り、Spec Kitも実態は spec-first 寄りと分析しています。一方、Tesslというツールは、spec-anchored や spec-as-source を目指しているそうです。

### SDDの課題

SDDは万能ではありません。先ほどの記事では、次のような課題も指摘されています。

- **レビューの負担**：ツールが大量のMarkdownを作るため、読むのが大変。筆者は「これだけのMarkdownを読むより、コードをレビューしたい」とまで書いています。
- **AIが仕様を守るとは限らない**：仕様やチェックリストを用意しても、AIが指示を無視したり、同じコードを重複して作ったりすることがあった、と報告されています。
- **モデル駆動開発（MDD）の失敗の繰り返しになる恐れ**：仕様から全部を作ろうとすると、かつてのモデル駆動開発と同じ「柔軟性のなさ」に、AIの「出力が毎回変わる」性質が加わる、と警告しています。

つまり、仕様を書いても、**出てきたものが仕様どおりかを確かめる仕組み**は別に必要です。ここでTDDの出番になります。

## SDDとTDDを細かく比べる

| 観点 | 仕様駆動開発（SDD） | テスト駆動開発（TDD） |
| --- | --- | --- |
| 目的 | 何を作るかの認識をそろえる | 作ったものが正しく動くことを確かめながら作る |
| 最初に書くもの | 要件・設計・タスクの文書 | 失敗するテスト1つ |
| 正（拠り所） | 仕様書 | テスト |
| 書く言葉 | 自然言語（EARSなどの型で半構造化） | プログラミング言語 |
| 判定 | 人とAIが読んで判断する（あいまいさが残る） | 機械が実行して判定する（成功か失敗か） |
| 粒度 | 機能・ユーザーストーリー単位 | 関数・振る舞い単位 |
| サイクルの長さ | 数時間〜数日 | 数分 |
| 関わる人 | 企画、設計者、開発者、AI | 主に開発者（とAI） |
| 見つけやすい問題 | 抜けている要件、決まっていないこと、認識のずれ | 実装のバグ、境界値の誤り、変更による壊れ |
| 見つけにくい問題 | 実装のバグ（読むだけでは分からない） | そもそも作るものが間違っていること |
| AIとの関係 | AIへの入力をそろえる | AIの出力を機械で確かめる |
| 生まれた時期 | 考え方は昔から。AI時代の手法としては2025年ごろから広まる | 1990年代末〜2000年代初め |
| よくある失敗 | 文書が増えすぎて誰も読まない | テストが実装の後追いになる |

表の「見つけやすい問題」と「見つけにくい問題」を見ると、**お互いの弱点をお互いが補っている**ことが分かります。

## SDDとTDDを組み合わせる

組み合わせ方は、とてもシンプルです。**仕様の受け入れ基準を、そのままテストにする**のです。

| 受け入れ基準（SDD） | テスト（TDD） |
| --- | --- |
| 1. 5,000円以上なら送料0円 | 合計が5,000円以上なら送料は0円 |
| 2. 5,000円未満なら送料600円 | 合計が5,000円未満なら送料は600円 |
| 3. 沖縄県は400円を加える | 沖縄県への5,000円未満の注文は送料1,000円 |
| 4. 負の数はエラー | 合計が負の数ならエラーになる |

EARSで書いた受け入れ基準は「〜のとき、〜する」という形なので、1つの基準がそのまま1つのテストになります。

### 流れ

1. **SDD**：要件をEARSで書き、決まっていないことを洗い出して、人が確認する
2. **SDD**：設計とタスクに分ける
3. **TDD**：タスクごとに、受け入れ基準をテストにして、失敗することを確かめる
4. **TDD**：テストが通るように実装し、リファクタリングする
5. **確認**：すべての受け入れ基準に、対応するテストがあるかを確かめる

5番目の「対応しているか」は、人の目だけだと漏れやすいところです。要件・実装・テストの対応表を作って、機械で確かめる方法もあります。たとえば私が公開している [ai-coding](https://github.com/shoyo-maya-bot/ai-coding) では、要件ごとに実装とテストの場所を表に書き、テストが実在してアサーションがあることをCIで確かめています。

### AIエージェントにTDDをさせるときのプロンプト

AIに実装を任せるときも、TDDの順番を守らせると品質が安定します。

> requirements.md の受け入れ基準1〜4を、1つずつTDDで実装してください。基準ごとに、先にテストを書いて失敗することを確かめ、そのあと最小限の実装でテストを通してください。テストの期待値は受け入れ基準から決め、実装に合わせて書き換えないでください。全部通ったら、テストが通るのを保ったままリファクタリングしてください。

最後の「期待値を実装に合わせて書き換えない」が特に大事です。AIはテストを通すために、テストの方を直してしまうことがあるからです。

## ほかの「〇〇駆動開発」

### 振る舞い駆動開発（BDD：Behavior-Driven Development）

TDDから派生した手法で、ダニエル・テルホルスト＝ノース（Daniel Terhorst-North）とクリス・マッツ（Chris Matts）が広めた「Given-When-Then」の書き方で知られます。TDDを教える中で「何をテストすればいいのか分からない」という混乱が多かったことから、「テスト」ではなく**振る舞い（behavior）**という言葉を使い、それを業務の言葉で書くことを重視します。

```gherkin
Feature: 送料の計算

  Scenario: 送料無料のライン
    Given カートの合計金額が 5000 円である
    And 配送先が 東京都 である
    When 送料を計算する
    Then 送料は 0 円になる
```

この書き方はGherkinと呼ばれ、Cucumberなどのツールで、そのまま自動テストとして実行できます。SDDの受け入れ基準と、TDDのテストの、ちょうど中間にある手法と考えると分かりやすいです。

### 受け入れテスト駆動開発（ATDD：Acceptance Test-Driven Development）

開発を始める前に、顧客や企画の人と一緒に**受け入れテスト**（何ができたら完成か）を決め、それを満たすように開発する手法です。TDDが「開発者の小さなテスト」から始めるのに対し、ATDDは「利用者から見た完成の条件」から始めます。BDDとよく似ていて、実例で仕様を書く「実例による仕様（Specification by Example）」とも深い関係があります。

### ドメイン駆動設計（DDD：Domain-Driven Design）

エリック・エヴァンス（Eric Evans）が2003年の著書で体系化した考え方です。名前は「設計（Design）」で、開発の手順というより**設計の考え方**です。

- **ユビキタス言語**：業務の専門家と開発者が同じ言葉を使い、その言葉をコードにもそのまま使う
- **境界づけられたコンテキスト**：大きな業務を、言葉の意味が一貫する範囲ごとに分ける

たとえば「会員」という言葉が、販売の部署と経理の部署で違う意味を持つなら、無理に1つにまとめず、別のコンテキストとして扱います。SDDで仕様を書くときにも、この「言葉をそろえる」考え方はそのまま役に立ちます。

### 機能駆動開発（FDD：Feature-Driven Development）

ジェフ・デ・ルカ（Jeff De Luca）が、1997年にシンガポールの銀行の大規模なプロジェクトのために考えた手法です。次の5つの活動で進めます。

1. 全体のモデルを作る
2. 機能の一覧を作る
3. 機能ごとに計画する
4. 機能ごとに設計する
5. 機能ごとに作る

利用者にとって価値のある小さな「機能」を単位に計画と進捗を管理するのが特徴です。

### モデル駆動開発（MDD：Model-Driven Development）

UMLなどのモデル（図や形式的な定義）を正とし、そこからコードを自動生成する考え方です。2001年に業界団体のOMGが、MDA（Model-Driven Architecture）という枠組みを打ち出しました。考え方としては今のSDDの「spec-as-source」に近く、モデルとコードの食い違いや、柔軟性のなさといった、当時の課題が今も参考になります。

### 契約による設計（DbC：Design by Contract）

バートランド・メイヤー（Bertrand Meyer）が、プログラミング言語Eiffelの設計とともに、1986年ごろから提唱した考え方です。関数ごとに3つの約束を決めます。

- **事前条件**：呼び出す側が守ること（例：合計金額は0以上）
- **事後条件**：関数が保証すること（例：送料は0以上）
- **不変条件**：常に成り立つこと

例題の「負の数ならエラー」は、事前条件をチェックしていることになります。

### 型駆動開発（Type-Driven Development）

先に型（データの形や、関数が受け取るもの・返すもの）を決め、型に導かれるように実装する考え方です。型で表せる制約が多い言語ほど効果が大きく、「ありえない状態を型で表せないようにする」ことで、バグの入る余地を減らします。

### スキーマ駆動・API駆動（Contract-First / API-First）

APIを作るとき、先にOpenAPIなどでAPIの定義（スキーマ）を書き、それを正として、サーバーとクライアントを並行して作るやり方です。定義からコードや型、テスト用のモックを生成できるので、チーム間の食い違いを減らせます。

### 名前が似ているけれど、開発手法ではないもの

**イベント駆動（Event-Driven）**や**データ駆動（Data-Driven）**も「駆動」と付きますが、多くの場合は開発の進め方ではありません。

- イベント駆動アーキテクチャ：何かが起きた（イベント）ことをきっかけに処理が動く、システムの作り方
- データ駆動：データにもとづいて判断する、意思決定の考え方

「〇〇駆動」と聞いたら、それが**開発の進め方**なのか、**システムの作り方**なのかを区別すると混乱しません。

## 一覧で比べる

| 名前 | 最初に書くもの | 正（拠り所） | 主な単位 | 主な読み手 |
| --- | --- | --- | --- | --- |
| SDD | 要件・設計・タスク | 仕様書 | 機能 | 人とAI |
| TDD | 失敗するテスト | テスト | 小さな振る舞い | 開発者 |
| BDD | Given-When-Thenのシナリオ | 振る舞いの記述 | シナリオ | 業務担当と開発者 |
| ATDD | 受け入れテスト | 受け入れテスト | ユーザーストーリー | 顧客と開発者 |
| DDD | ドメインモデルと共通の言葉 | ドメインモデル | コンテキスト | 業務の専門家と開発者 |
| FDD | 機能の一覧 | 機能の一覧 | 機能 | 管理者と開発者 |
| MDD | モデル | モデル | システム | 設計者 |
| DbC | 事前・事後条件 | 契約 | 関数 | 開発者 |
| スキーマ駆動 | API定義 | API定義 | API | 複数のチーム |

## どう選ぶか

| 状況 | おすすめ |
| --- | --- |
| AIに機能をまるごと作らせたい | SDDで仕様をそろえ、実装はTDDの順番で |
| 計算や判定のロジックを書く | TDD |
| バグを直す | TDD（まずバグを再現するテストを書く） |
| 企画や業務の人と完成の条件を合わせたい | BDD・ATDD |
| 業務が複雑で、言葉の意味が人によって違う | DDD |
| 複数のチームでAPIをやり取りする | スキーマ駆動 |
| まず作ってみないと分からない試作 | 無理に駆動開発をしない。方向が決まってから仕様やテストを整える |

1つに決める必要はありません。実際の開発では、DDDで言葉をそろえ、SDDで仕様を決め、BDDで受け入れ基準を書き、TDDで実装する、というように重ねて使うことがよくあります。

## よくある失敗

**SDDで文書を書きすぎる**
要件・設計・タスクを細かく書くほど、読む人の負担が増えます。読まれない仕様は、無いのと同じです。まずは受け入れ基準と「決まっていないこと」だけでも十分に価値があります。

**TDDのテストが、実装の後追いになる**
実装を書いてから、その動きに合わせてテストを書くと、テストは「今の動き」を写しただけになります。AIに書かせるときは特に、期待値は仕様から決め、実装に合わせないよう指示しましょう。

**仕様とテストが別々に育つ**
仕様を直したのにテストが古いまま、またはその逆、ということが起きがちです。受け入れ基準とテストを対応させ、どちらかを変えたらもう片方も見直す運用にします。

**「〇〇駆動」の名前にこだわりすぎる**
手法は目的ではなく道具です。チームが抱えている問題（認識のずれなのか、バグなのか、言葉の混乱なのか）に合わせて選びましょう。

## まとめ

- **SDD**は「何を作るか」を先に文章で決め、人とAIの認識をそろえる手法
- **TDD**は「正しく動くか」を先にテストで書き、小さな歩幅で作る手法
- SDDは作るものの間違いに強く、TDDは実装の間違いに強い。だから組み合わせると強い
- 組み合わせるコツは、**受け入れ基準をそのままテストにする**こと

AIがコードを書く時代になっても、「何を作るか決める」と「正しく作れたか確かめる」は人の仕事として残ります。SDDとTDDは、その2つをAIと一緒に進めるための、心強い道具です。
